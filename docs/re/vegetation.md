# Battle vegetation: how the game places and draws it (2026-10-18)

Method: Ghidra on `empire.retail.dll` (project `~/startpos_research/ghidra`, headless, `-noanalysis -readOnly`), the game's compiled tree shaders
(`rigidbranch_v3`, `rigidleaf_v3`, `rigidleafcommon_v3`, the billboard shaders) and BOB's packed output of `western_city_rome/medium`.
Rendering side: `docs/re/renderer.md` (tree vertex formats, instance rows, LOD) and `crates/wce_render` (the tree G-buffer and shadow passes).

## Static and procedural trees

A tile has two kinds of trees:

- **Static**: the `VEGETATION_INSTANCE` elements of `tile.ted` (`key="<species>.<variant>"`, model
  `battleterrain/vegetation/trees/<species>/<variant>.rigid_model_v2`). The editor draws them from tile.ted.
- **Procedural**: generated by BOB (BOB_Vegetation, "stage C" in `docs/plans/tile.md`) from the tile's seeds (`<Vegetation generation_seed=...>`,
  `<Grass generation_seed=...>` in tile.ted, `tree_random_seed.xml` of raw tiles) and the vegetation painting, once per climate key with
  `per_climate_tree_conversions.xml` / `tree_climate_conversions.xml`. BOB writes the result, static trees included, into the packed tile:
  `<key>.tree_list.bin` (`default`, `rome_med`, `rome_desert`, ..., `outfield_tents`) and `default.grass_list.bin`.

The game reads only the lists: tile.ted is not shipped. `FUN_1184eeb0` builds the tile's file names (`<key>.tree_list.bin`, `.tree_list.xml`,
`default.tree_list`, `outfield_tents.tree_list.bin`, `default.grass_list.bin`, ...) from the climate key it is given.

Measured on Rome (`rome_med`, 22,478 trees): 15,641 list trees stand exactly (within 2 cm) where a static instance stands, the static instances of
the layers hidden in TEd included; the rest are generated. The other climates' lists hold the same positions with other species
(`rome_desert`: stones and chenopods; `rome_continental`: oak and spruce).

### List file (`*.tree_list.bin`, rpfm `TreeListFile`)

`FASTBIN0`, `u16 serialise_version` (1 in the packs, 1 to 3 known), `u32 n_types`, then per type `str model` (mixed case, backslashes:
`BattleTerrain/vegetation/trees\pistacia\pistacia_b.rigid_model_v2`), `u32 n`, n x item. The item reader is `FUN_10d88c40`:

| Bytes | Field | Notes |
|---|---|---|
| f32 x 3 | `x`, `y`, `z` | x and z in world metres, z counted from the far edge (world z = tile extent - z), y in scene units (world y = y / unit_scale) |
| u8 | `scale` | the tree's scale x 127 (127 = 1.0; generated trees 89..253, so 0.7..2.0) |
| u8 | `is_freeform` | 1: the stored height; 0: the tree is put on the terrain |
| u8 | `is_burnable` | version 2 only |

The item has no rotation. In memory the item is 16 bytes (x, y, z, pad, scale, is_freeform). rpfm stores the scale byte in `BattleTreeItem::scale` as
byte / 127 and `is_freeform` in `flags`; `is_burnable` was `uk_1`.

### Placement (`FUN_10429b80`, called per list type through the job splitter `FUN_103fdbd0`)

Per tree:

1. `scale = byte * (1 / 127)` (constant `0x11b3f300`).
2. Height: when `is_freeform == 0` and the tree is inside the tile, the terrain height at (x, z) replaces y.
3. A terrain normal from four height samples 0.5 m around the tree, and a tilt basis that takes the model's up axis to it.
4. Yaw: MSVC `rand` LCG, `state = state * 0x343fd + 0x269ec3`, `yaw = (state >> 16) * 9.5875e-5` (2 pi / 65536, `0x11b26b34`). The state starts at
   `0x49710ae3` at the start of every job, and the splitter cuts a type's list into jobs by the worker count
   (`max(grain, n / ((workers * 5 + 5) * 4))`). The game's yaws therefore depend on the machine's thread count. The state advances only for
   trees that pass the visibility checks.
5. Two 3x4 matrices per tree into the 0x9c-byte record: `P1 * tilt * yaw * scale` and `P2 * yaw * scale` (P1 and P2 are per-type matrices, `piVar9[7]`),
   translated to the position.

The tweakers `MIN_TREE_SCALE` (0.8) and `MAX_TREE_SCALE` (1.2) of TreeDisplay.cpp (objects `0x122b60d8` / `0x122b5f88`) drive the random scale of
another tree path (`FUN_1042ca50`, same seed, same LCG). That path draws a random scale and yaw and ignores the list's scale byte. Which trees it serves
(frontend backdrop, `FRONTEND_BACKDROP_MIN/MAX_TREE_SCALE` are separate tweakers) is open.

The editor (`crates/wce_tile_editor/src/tile_document/vegetation.rs`) draws one list chosen on the Tile panel (*procedural trees*; command
`tree_list [name | none]`, default `default`). It skips the list trees that stand where a shown static instance stands, puts non-freeform trees on
the terrain, scales by the byte / 127, uses the one-worker yaw sequence and tilts the tree to the terrain (step 3, normal from the world heights
0.5 m to each side). The static VEGETATION_INSTANCEs are drawn tilted too (they are list trees in the game); their edit gizmos and picking keep the untilted matrix.

### Grass (`default.grass_list.bin`, rpfm `GrassListFile`)

Items are three halfs: x, the height, z (list frame as the trees': z from the far edge), grouped by key `<texture group>/<index>`
(`grass/2`, `forest/0`, `settlement_1/3`...). 189 packed tiles have one (farms, encampments, settlements, custom tiles).

**Game placement** ("Grass Display" FUN_105103e0, its job FUN_10515960 through the splitter FUN_10507520). Per key, the model is
`<key>.rigid_model_v2` resolved by the model lookup (in the climate's `terrain/vegetation/battle/grass/<climate>/` folder; climates lack some
groups, which the `default` folder has). Per patch: x at +0, z at +4 (the height at +2 is read but unused). It takes the terrain height there
and the terrain normal from the heights h = max(the model's x / z extent, 0.4) · 0.5 metres to each side (a central difference over the
patch). It drops a patch whose model box is not inside a square of half-size s around the battle's
origin (s from the grass system's virtual +0x78), and one whose normal.y is not above
cos(`GRASS_ANGLE_CULL_AMOUNT`, a tweaker at 0x122c95a8, default 0.7 rad). For a kept patch the LCG steps: a 32-byte record (model, position,
normal, yaw). The LCG is seeded with 0x49710ae3 per job (chunks of 1024 items × workers: the one-worker sequence is per key),
yaw = (s >> 16) · f32(0x38c910a4). There is no scale. The editor tilts the patch to that normal and turns it by the yaw.

**Shaders** (`rigidgrass.hlsl`; the shader object FUN_116e69f0 builds `shadowmap`, `zprefill` + `gbuffer_zequals`, `gbuffer`, `gbuffer_ms` and
OIT variants).
- Vertex (Grass format, 28 bytes): POSITION0 f16×4 (around the material's pivot), TEXCOORD0 f32×2, NORMAL0 / NORMAL1 u8×4, COLOR0 u8×4
  (alpha: how much the vertex sways and sinks, 0 at the roots).
- Instance: TEXCOORD1..3 are the 3×4 world rows, TEXCOORD4.xy the burn.
- vs30_main_grass sways the tips with `wind_VS`. It sinks them with the camera distance: y' = (1 − a · min(d / 100, 1)) (y + 0.6) − 0.6.
  So the grass is gone at 100 m.
- ps30_gbuffer_grass alpha-tests the diffuse against `s_dissolve_map` (`commontextures/dissolve.dds`, at uv × 100 and uv × 20 with the
  blade's facing, so edge-on blades fade). It details the colour with the terrain's mid / near detail maps (`ps_height_map_cb`).
- It writes the normal, sqrt(colour), specular (1, 1, 1, 0) and z / w. Its alpha fades the patch with distance where the scene behind it is
  close (`s_depth_map`, linear view depth).
- The `gbuffer` blend state: RT0..2 src alpha / inv src alpha, alpha zero / inv src alpha.
- `grass_PS`: the grass draw FUN_118858a0 (the render node's vtable at 0x11cbda34..) sets:
  - `g_alpha` = (`grass_alpha_mul` 2.5, `grass_alpha_add` 0): tweakers from RigidMesh_v2.cpp. The roots (colour alpha 0) blend into the ground.
  - `g_inv_lod_distance` = 1 / the grass system's integer at +0x80. No grass shader reads it (cb[0].x of `grass_PS` in none of the
    gbuffer, z-prefill, no-clip, MSAA, shadow or OIT variants). The extent is the shaders' own 100 m: the tips reach the roots, and the
    alpha reaches 0 there.
  - `g_normal_scale_bias` = (1, 0), or (2, −1) for a flagged normal map.
  - The rest keep the constructor's defaults (FUN_116d8090): `g_far_scale` (0, 0), `g_clip_bias` 0, and `g_far_addition` −1, which turns
    the `s_far_diffuse_map` tint off: sat(g_far_addition − colour.w + 1) = 0.
- Techniques (FUN_118900c0, per render pass): the shadow pass draws `shadowmap` (grass casts shadows, as the leaves). The G-buffer pass
  draws `gbuffer`, or `zprefill` then `gbuffer_zequals` with the z-prefill on, or `gbuffer_ms` with MSAA.
- Textures (the material resolver FUN_1186c880):
  - `test_gray` / `test_black` / `test_mask` / `test_white` / `test_gloss` / `flatnormal` names become `CommonTextures/default_*`.
  - The grass render node (constructor FUN_117c74a0) loads `commontextures/dissolve.dds` for `s_dissolve_map`. A global weather object
    (FUN_118ce490) loads `commontextures/snow_normal.dds` for `s_snow_normals`.
  - With seasons, a `<prefix>_diffuse<rest>` texture loads `<prefix>_<season>_diffuse<rest>` for sp / su / au / wi where it exists, and
    `_br` / `_sn` variants. The climate grass folders have `grass_su`, `grass_au`, `grass_wi`, `grass_sp`; summer `rome_continental` grass
    is poppies.
  - With alpha blending on (manager+0x716bc, the setting that "Disabled Alpha-blending" turns off: 2, or 1 with more than 2 of the
    value at vfunc +0x128), the diffuse of two material types becomes `<name>_ab.dds`. These are the OIT grass techniques' textures; the
    G-buffer path uses the plain ones.
  - A texture that doesn't load falls back to `CommonTextures/default_white`. The editor instead looks under the same name next to the
    model (the `default` models name rome_atlantic textures that are only in their own folder). That gives `default/mud/2` (whose
    texture names a legacy `battleterrain/...` path) a pale blue-white tuft; the game would draw it white.

**BOB's generator** (`ACTION_GRASS::run` FUN_10007570 in BOB_Vegetation; `EMPIREUTILITY::PROCEDURAL_GRASS`; port:
`wce_tile::vegetation::grass`).
- Seed: `<Grass generation_seed>` of tile.ted. Parameters: `terrain/vegetation/battle/grass/max_grass.xml` (kit working_data): the default
  and per-group densities (patches per square metre), the default and per group / index thresholds.
- `generate_grass`: for each texture group of the tile, in name order (a std::map of name → its textures), the trees' point generator
  (FUN_102ae400) draws the group's density of points. The random state runs on from group to group; the discard test is a box (none in effect).
- `pick_models` / `choose_grass_for_pixel` for each point:
  - Per group, the sum of its textures' positive channels, and the strongest channel (index 0..3 within its texture).
  - The group with the largest sum wins (strictly larger: the first on ties; the scan stops at a sum of 1).
  - The point becomes `<group>/<index>` if the threshold for (group, index) ≤ that channel's value.
- The patches go into a VECTOR_2 → info map (first stays). In the map's order, they go to the list frame (x / rs, (cells_y · 256 − y) / rs;
  off-tile ones are skipped) and the height of the bordered map pixel (round(tri + x / cell), ...).
- They are pushed as (key, item) onto a vector **sorted by key with MSVC's std::sort** (FUN_10007150: VS2010 introsort, median of 3 / of 9
  over 40, insertion sort up to 32, heap sort when the depth budget runs out; `wce_tile::vegetation::msvc_sort`). It is not stable: it
  decides the order of a key's patches, and with it their yaws in the game.
- **The trees go through the same sort** (by their case-sensitive model path): with it the generated tree lists are in BOB's order too.
  Paths that differ only in case are separate lists.

Verified (`cargo run --release -p wce_tile --example grass_check -- <game>`): 119 of the 125 kit tiles with a packed list are exact, the order
of every key included. The 6 others are settlements with ~700k patches each, every one over 98.9% equal. eastern_city_b has the same
positions with other keys in local clusters: their raw blend maps drifted from the packs.

## BOB's generator (BOB_Vegetation + EmpireUtility, 2026-10-18, in progress)

Ghidra project `/tmp/wce_re/bob_proj` (`EmpireUtility.AssemblyKit.dll` with its exported names, `BOB_Vegetation.AssemblyKit.dll`). The generator is
`EMPIREUTILITY::PROCEDURAL_OBJECTS` (ProceduralObjects.cpp, ProceduralPointGeneration.cpp, ImageValueDataProvider.cpp); BOB_Vegetation's action
(`FUN_100477a0`) drives it once per generation category (`generation_categories.xml`: default, ROME_Atlantic, ..., outfield_tents).

**Inputs** (prepare action `FUN_1004bc40`):
- Heights: `height_map_0.png` converted to floats, then `h * variation.scale + variation.min_height` (`FUN_1004ad30`).
- Blend: `blend_map.tif` (1 mip, 16 x L16) converted to 16 floats per pixel. A texture is 4 channels; texture i is the tile's custom texture
  group i (`TILE::custom_texture_group_name`, the ground groups settlement_1 .. forest), so a channel is `texture * 4 + channel`. A channel
  value is divided by the sum of its texture's 4 channels when that sum is over 1 (`FUN_1028bb40`).
- Cells: every subtile with `TILE::subtile_masked_valid(x, y)`, stored as (x, height - 1 - y). A pixel's cell is
  `floor(f32(p / (0.5 - border)))`; outside the set every blend and height value is 0.
- Seeds: `<Vegetation generation_seed decal_generation_seed vfx_generation_seed>` of tile.ted. Exclusion: the
  `VegetationExclusionPolygonInstance` outlines (a candidate inside one is discarded).
- Three generators per category: object mask 3 (tree | prop) with `generation_seed` and density `max_trees_per_metre_squared`
  (`per_climate_densities.xml`), 4 (decal) with the decal seed and `max_decals`, 8 (vfx) with the vfx seed and `max_vfx`. Humidity 0.

**Pixel grid** (`IMAGE_VALUE_DATA_PROVIDER`, `FUN_102adc30`): `border = trunc(0.5 - tri_density)` (-127 for 128),
`W = (cells_x + 2) * tri_density + 2 * border` (the tile plus one pixel each side: 1026 for an 8-cell tile), the same for H, and the cell size
`m_terrain_tile_size / tri_density * render_scale` (2.0 on Rome: BOB works in scene units). Pixel (i, j) reads the 1280-wide maps at
(i - border, j - border).

**Candidates** (`PROCEDURAL_POINT_GENERATION::generate_points`, `FUN_102ae400`, SSE single precision, x87 only for the conversions):
`total = f32(W * H)`, `n = cell * cell * total * density`, `N = ceil(n)` (if `N >= total`: `n = total - 1`, `N = ceil(n)`), `total2 =
ceil(total / n * ceil(n))`. N distinct keys: `u1 = lcg(s)`, `u2 = lcg(u1)`, `s = u2`,
`v = (hi(u2) * k) * (total2 * k) + total2 * (hi(u1) * k)` with `k = 1/65535` and `hi(u) = u >> 16`, redrawn while v is taken or `v >= total2`. Then
the pixels in order (x outer, y inner) with a counter c = 1, 2, ...: a pixel where the smallest remaining key is <= c consumes every key <= c and
becomes a candidate at (cell * (i + 0.5), cell * (j + 0.5)) unless it is discarded; the walk stops when the keys run out (that pixel is not added).
Verified on Rome's `default` list: every generated tree (x.5, z.5) is a candidate, with list x = px / cell and list z = 1024 - py / cell.

**Per candidate** (`generate_objects_internal`): height h of the pixel; a group (`choose_group_for_position`: each group of the category whose
`channel_group` texture sum is over a threshold gets weight `channel_range_probability(value of channel_group_for_probability / channel_number)
+ height_range_probability(h)`, cumulative in the map's order, one LCG draw `hi * k * total`); the group's objects of the generator's mask get
weight `blendmap_range_probability(sum of the group's channel textures) + height_range_probability(h)`, one draw picks one; its size is
`size_low + hi(lcg) * k * (size_high - size_low) * blend_sum`. Then `group_objects` (an object with grouping probability re-rolls neighbours
within its grouping radius) and `remove_objects_based_on_min_seperation`.

**Group objects** (`group_objects`, after every candidate): the chosen objects in the order of a `std::map` keyed by (min_sep, x, y); an
object whose current group has a grouping probability and radius draws `hi * k`, and when that is <= the probability every other object
within the radius (quadtree query, then each node's entries in bucket order) whose pixel is valid for the leader's group (`valid_group_for_position`:
group texture sum >= 0.05 and a non-zero channel-range probability of the group's probability-channel sum) is re-rolled from the leader's
group (weights from the candidate's stored blend sum and height): model, group name, min_sep, outfield flag and size change (two size draws:
the generated map's copy keeps the first, the quadtree's copy the second); width, type and the grouping values stay.

**Minimum separation** (`remove_objects_based_on_min_seperation`): over a copy of the generated map (bucket order), every object still present
with min_sep > 0 queries the quadtree with its radius and removes each other object within either's reach (points: squared distance against
min_sep²; objects with a width: the circle against the width box, `FUN_10a858a0`). **After an erase BOB's loop advances twice**, so the entry
following a removed one in that node is not looked at; reproducing this was the last difference.

**Quadtree** (`AABB_2_STATIC_QUADTREE`, 7 tiers): bounds = the candidates' bounds +-0.5; children (low x, high y), (high x, high y), (low x, low y),
(high x, low y); an object goes into the deepest node containing its +-0.01 box; a query visits nodes depth first, a node fully inside the circle
adds its whole subtree, a node touching it adds itself (when it has entries) and recurses. Position maps hash `bits(x) ^ bits(y) ^ 0x4a545eed`.

**Output** (BOB_Vegetation): the generated map in bucket order; type 1 (tree) objects go to the tree list at (x / 2, (cells_y * 256 - y) / 2) for
Rome's 2.0 scale, height sampled from the height map (x 0.5 m rounding), scale byte `ceil(size * 127)`, is_freeform 0, model path
`BattleTerrain/vegetation/` + model + `.rigid_model_v2`.

**Verified** (Python prototype `/tmp/wce_re/proto`, then the Rust port): every generated tree of `attila_steppes_plains/1x1/aa` (ROME_Med 184,
ROME_Destruct 196, ROME_Destructdes 62) equal to the packed lists in position, model and scale byte. Rome's raw tile drifts from its packed lists
after the first columns (the kit's Rome raw data is not the revision CA built the packs from).

**Corpus** (`cargo run --release -p wce_tile --example veg_check -- <game>`: every Assembly Kit tile's generated trees against its packed
`<category>.tree_list.bin`): 1,969 of 2,788 lists exact, 138 more over 90%. ROME_Med 599 / 640, ROME_Destructdes 606 / 650; the rest is below.
Also verified on the corpus: the grid uses the variation's `raw_data_tri_density`; the scale byte wraps (`ceil(size * 127) as i64 & 0xff`),
it doesn't saturate; trees whose model file doesn't exist are dropped; exclusion polygons include hidden ones.

**Parameter semantics** (`parse_object_parameters_xml`, `generate_objects`, `choose_group_for_position`): the objects map is keyed
`group + "_" + model` and keeps the first definition; the category and humidity maps hold pointers into it, so a later file that puts an existing
key in another category gives that category the first file's parameters. Groups keep their first definition too. A generator's groups come from
the category map filtered by the humidity map, grouped by each object's own (first) group name; the global group -> objects map the parser also
fills is not used. Measured on ROME_Destruct (whose destruct* files redefine atlantic* groups with other values): first-wins for both 293 / 654
exact, last-wins objects 122, last-wins groups 32, both 29; per-category definitions (each category gets the file that first put the key in it)
are worse too. The group choice keeps its cumulative weights in an ordered set keyed by the running total (an addition that leaves the total
unchanged is dropped) and takes the first total >= draw, which a cumulative vector reproduces. No group: "cherry", which matches nothing.

**Ranges**: a range with a falloff is (low, high, inner_low, inner_high). Objects: when `high - low < falloff`, `d = (high - low - falloff) / 2`
(negative: the plateau gets wider than the range), inner = (low + d, high - d), else inner = (low, high). Groups: when `falloff < high - low`,
`d = (high - low - falloff) / 2`, inner = (low + d, high - d), else inner = (low, high). A group channel value of exactly 0 has probability 0;
heights equal to the low end get +0.001 first. Weights add (height + blend), in f32, cumulatively. Probability: p inside inner, a ramp from low to inner_low and from inner_high to high,
0 outside.

**Containers** (the order of every draw depends on them): `CA_STD::UNORDERED_MAP<CA::String, ...>`: 4 buckets, max load 1.0, grows to
2n + 1 buckets when `count / buckets > 1` after counting the new key, rehash keeps each bucket's order; a key goes to the end of bucket
`hash % buckets` with `hash = 0xf73a51c9 ^ (s[len-1] << 0) ^ (s[len-2] << 8) ^ (s[len-3] << 16) ^ (s[len-4] << 24) ^ (s[len-5] << 0) ...`
(signed chars); iteration is bucket by bucket. Parameter files: every `BattleTerrain\vegetation\*tree_parameters.xml`, `tree` / `prop` /
`decal` / `vfx` / `group` children.

## Tint colours (`g_tint_colours`)

The leaf and billboard shaders read `g_tint_colours` for the per-instance tint (the instance seed picks between the colours). In the dll:

- The leaf shader constructor `FUN_116e5130` declares `g_tint_colours` with the default (1, 1, 1, 1); the variable object is at +0x2f0, its slot
  pointer at +0x304. The billboard shader constructor `FUN_116ebbb0` does the same.
- The `RIGID_LEAF_DRY` / `RIGID_LEAF_WET` shader objects sit at manager+0x60bf8 / +0x63420 (manager `FUN_1178c460`). They are used only by the shader
  registry `FUN_116f1a30`, the destructor `FUN_117134e0`, the technique-select thunk at `0x11843fb4`, and the leaf draw `FUN_11885aa0`. The draw
  writes only `g_billboard_params` (shader+0x334, through `FUN_11883540`).
- The `tint_min/max` and `ColourTintMin/Max` strings belong to particles.

Conclusion: the engine never writes `g_tint_colours`, so the trees are untinted (white), as the editor binds them. Caveat: a generic writer
that sets variables by name hash would not show up in this search; only a memory dump of a running battle would rule it out.

## Open

  distance). Candidates: the leaf cards' alpha test threshold (`g_billboard_params` from `FUN_11883540` is not fed yet), the LOD weights of the leaf
  vertices (`LOD weights@44`), or the leaf size scaling with distance in `rigidleafcommon_v3`'s vertex shader. To look at after the procedural
  vegetation.
- **Procedural generation.** `wce_tile::vegetation` reimplements the tree and grass generators (above); the editor generates a list the tile
  has no packed file for (or `gen:<list>` / grass *generated*). Open:
  - The atlantic family: ROME_Destruct on forest tiles (293 / 654), the climate lists of settlements, farms and roads (rome_atlantic
    73 / 121) and outfield_tents (the `atl_yurt*` groups). All use atlantic-style parameter files; ROME_Med (599 / 640) and
    ROME_Destructdes (606 / 650) don't. The main loop's random stream stays in step, so the difference is in grouping or the minimum
    separation. Traced on farm_eastern/1x1/ab: BOB kept a separation-3 stone that mine removed. Mine had re-rolled a neighbour exactly on
    a leader's grouping radius (2) to a separation-1 stone, which then removed it. BOB evidently didn't re-roll it, and the shifted
    grouping draws change the rest.
    Checked against the decompile and found equal:

      the neighbour's blend and height, the type mask, the two size draws;
    - valid_group_for_position: the channel group sum, then the probability group's sum through the zero-checked channel range;
    - the quadtree: build, container, depth-first query, circle-box test;
    - the CA map: insert, rehash and copy order;
    - remove_objects_based_on_min_seperation: the outer loop over a straight copy of the live map, the skip after each erase.

    are identical to farm_sassanid's (which has tents) apart from the location, so those lists look stale. The yurt file's only
    `<include_in_outfield />` has a non-breaking space before `/>`, so in BOB no object has the flag.

    in a DLL not imported yet) at the tree's pixel. The game ignores the stored y (trees go on the terrain).
  - Not done: props / decals / VFX outputs, merging static trees, the per-climate conversions on write.
- **Grass, settled as far as the game's static code goes:**
  - The playable-area box: the tile's grass list is moved into the battle's frame (`GRASS_LIST::transform`, a 4×3 matrix per tile
    when the battle map is assembled) and patches must fit in ±s around the battle's origin. That depends on the battle, not on the
    tile, so the editor draws the whole tile.
  - `gfx_grass_quality`: the preference becomes `GRASS_QUALITY` in the graphics presets (FUN_11725c30, preset +0x30, manager
    +0x7167c). The only reader is a virtual getter (manager vtable +0x21c), and no call to it was found in the binary. Nothing in the
    grass placement, constants, shaders or technique choice depends on it. The editor draws the maximum (what the user's preferences
    have).
  - The seasonal path: the resolver's flag comes from the node base (FUN_117be1b0): 1 when an id the node factory holds
    (FUN_1185b0c0's `this`+0xc, not the mesh's material type) is 0x40, 0x5b, 0x5c, 0x6e or 0x6f. The tree and grass nodes come from the
    same factory call, and the battle trees ship the seasonal diffuses in bulk (~340 per season: `oak_au` / `oak_sp` / `oak_wi`; summer is
    the plain name unless a `_su` exists, as for the grass poppies). So battle vegetation takes the path; what the factory id is was not
    traced further.
  - The editor does the swap for grass and for the trees' branches, leaves and billboards (G-buffer and shadow passes), from the scene's
    `vegetation_season` (the tile's ground season).
- `tree_metadata.txt` LOD distances vs the models' own.
- The second instance matrix (untilted) vs the shader's TEXCOORD0..2 / 3..5: the editor feeds the tilted matrix to both.
