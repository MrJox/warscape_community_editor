# tile.ted (scene graph of a tile)

XML, `<project version="N">` with N in {1, 6, 8, 9, 11, 12, 14, 15, 16, 17} (850 files are v16, 52 v17). Read and edited with `src/scene/ted_scene.*` on top of the lossless `XmlDoc`; gate `tools/scene_check` (1,393 files, 1.47 M instances, 3.24 M numbers).

Structure: `modules` (`Vegetation` generation_seed(s), `Grass`, `Particle_Effects_VFX` seeds), `scene` > `SCENE_GRAPH` > `children` > layers and instances, `camera`. Layers: `LayerInstance` (export_type `LayerExportType_Normal|Escalation1..3`), `UserInstanceGroup`, `INSTANCE_GROUP`, `LAYER_INSTANCE_GROUP` (older). Every instance has `flags` (`OIF_VISIBLE|OIF_ACTIVE|OIF_DRAGGABLE...`), `lf_offset`, `name`, `position`, `orientation`, `surface_mode` (`MSM_FREEFORM`, `MSM_LANDSCAPE`).

Instance types in the corpus (count of instances with a position, files up to 12 MB): VEGETATION_INSTANCE 427k, BUILDING_INSTANCE 347k, ProjectedDecalInstance 310k, UserInstanceGroup 339k, VFXInstance 7.3k, SIEGE_AI_POLYGON_INSTANCE 7.1k, AI_HINT_POLYGON_INSTANCE 5.7k, POINT_LIGHT_INSTANCE 5.4k, VegetationExclusionPolygonInstance 2.9k, NOGO_REGION_POLYGON_INSTANCE 2.4k, SIMPLE_MESH_INSTANCE 1.3k, SiegeAINode/EdgeInstance 1.3k/1.8k, ZONE_POLYGON_INSTANCE, DEPLOYMENT_ZONE_POLYGON_INSTANCE, DeploymentZonePolygonInstanceGroup, CaptureLocationInstance + CaptureLocationPolygonInstance, CivilianDeploymentZone, CivilianShelter, GO_REGION_POLYGON_INSTANCE, AISeparatorInstance, SplineRiverInstance, SEGMENTED_SPLINE_INSTANCE, LiteBuildingZone. Polygons carry a `points` child (`<point position="x,y,z"/>`); rivers carry points with width / foam_amount / alpha_fade / flow_speed / controlIn / controlOut / terrain_offset.

BUILDING_INSTANCE attributes: key (battlefield_buildings key), building_tech_level, burn, burn_amount, destruction_level, dirt_level, glow_amount, indestructible, toggleable, opacity, bounds_colour. VEGETATION_INSTANCE: key, scale. ProjectedDecalInstance: key, parallax_scale, scale, tiled. VFXInstance: vfx, autoplay, scale, seasons, use_in_outfield.

## Number formatting (reproduced for 100% of 3,244,021 values)
`vector(x,y,z)`, `euler(x,y,z)` (radians), uniform or vector `scale`, `area`, `radius`, `opacity`, `flag_position/flag_facing`: float32, `%.6f` rounded **half away from zero**, trailing zeros and a trailing `.` removed (`-0.000000` stays `-0`). `<point position="x,y,z">`: `%g` (6 significant digits, e.g. `-6.86646e-05`). Colours `argb(a,r,g,b)` use the same rule.

## Editing
Attribute edits only (the text outside the edited value is untouched); setting a value equal to the current one (as float32) is a no-op; `revert_all` restores the original bytes. Structural edits (add / remove / duplicate instances) go through `XmlDoc::{with_child, removed_element, duplicated_element}`.

## Where the height map sits (measured in Phase 6)
`height_map_0.png` is not stretched over the tile. It has a border of one cell (128 m) on every side: its size is `(cells + 2) * ppc` pixels per axis (`cells` = TILE `width` / `height` of the tile database, `ppc` = pixels per cell: 128 for the settlement tiles, 32 for monte_rosa), one pixel per `128 / ppc` metres, pixel (0, 0) at (-128, -128) m in the tile's frame (x = scene x / 2, z = scene z / 2), rows run along +z, no flip.
Evidence: on `western_city_rome/medium` (8 x 8 cells, 1280 px) the instance heights of the 94,000 buildings and trees sit on the height map with a mean error of 0.68 m (median 0.06 m) at offset 128 m / 1 m per pixel, against 1.9 m when the map is stretched over the 1024 m tile; a search over offsets and scales has its minimum at exactly that offset and scale, and flipping z makes it worse (1.7 m). `TileProject::pixel_x / pixel_z / height_at` implement it; without a tile database entry the map is stretched over the tile as the Phase 1 code did.
Instance orientations: `euler(a, b, c)` is `Rz(c) * Ry(a) * Rx(-b)` (above); the tile tool draws the building models with that matrix and the buildings of the Rome tile line up along the streets, but the handedness of the game's frame against TEd's (building_list.xml flips z) is not checked pixel for pixel.


## Against TEd's own export (Phase 0, 2026-10-09; `cli/placement_check`, `docs/baseline/placement_check.txt`)
TEd's stage A export `working_data/.../building_list.xml` (`BATTLEFIELD_BUILDING key position_x/y/z position_type orientation_i/j/k/w scale_x/y/z ...`, `position_type='lf_relative'` in all 373,955 entries) is the oracle for building transforms. For 357,666 buildings of the 73 kit tiles that have one:
- `position_x` = the tool's world x (scene x / 2), `position_z` = tile length in z - the tool's world z (the export mirrors z about the tile: 1024 m for an 8 x 8 tile), `position_y` = the tool's world y: **absolute metres** in spite of `lf_relative`. Maximum error 0.0001 m. 15 crates (freeform groups nested under a landscape group) are up to 2.70 m off.
- The quaternion `(i, j, k, w)` equals the tool's world rotation `Rz(c) * Ry(a) * Rx(-b)` as is (0.00 degrees); mirroring it with the z flip is 90 degrees off on average.
- Landscape buildings sit on `min_height + scale * raw / 65535` of the tile database entry with a median error of 0.000 m (94 % within 5 cm, 6 % off by 5 cm to 5 m: stored as snapped by TEd at placement, not re-snapped on save / export); freeform ones are free (median 0.59 m above the terrain). `surface_mode` changes how TEd edits an instance, not the numbers in the file. Five TDD tiles (`dead_marshes` 1x1 / 2x2, `lothlorien` 1x1 / 2x2 / 4x4) do not fit their entry's `min_height` / `scale`.
- **Models are drawn at 1 / unit scale** (2026-10-18, `western_city_rome/medium` against TEd screenshots): positions are half metres horizontally
  (unit scale 2) and in the tool's world (scene x, z / 2) a building's geometry is
  scaled by 1 / unit too (`Tile::world_matrix`). Drawn at full size, every building was twice as wide as its spacing (the city
  overlapped itself, the colosseum's 8 wedges made a swirl, the circus straights overlapped). Evidence: the colosseum's wedge apex
  (vertex frame (-2.84, 55.59) + pivot (30.21, 18.33), halved) lands on the group's centre for all 8 instances (local (13.69, 36.96) against
  (13.69, 37.04)); the circus straights (31.5 m long) are 31.0 scene units apart; the painted roads of the terrain line up with the streets;
  colosseum-to-neighbour distance over its diameter is 1.45 (TEd 1.42). The game's own `building_list` positions are the tool's (27,681 of
  27,680 + 3,487 escalation buildings to 5 cm), so placement was never wrong. The tool's whole world is scene space / unit on **every** axis
  (`tile_document/mod.rs`): heights (terrain, instance y, rivers, polygons, markers) too. With y left in scene units the terrain and every
  height were twice as tall as TEd shows them, and the stone bridges (group y -15.6, deck 17.9 above the model origin) stood under the banks;
  halved, the deck is 2 units above the banks as in TEd. The export and the game's lists keep scene units (`placement_check` compares in them).
- **Layer flags, measured in TEd** (2026-10-10, a probe copy of `tdd_custom_lothlorien/1x1/aa`, toggling in the Property Editor's Scene tab and diffing the saved `tile.ted` with `scripts/span_diff.py`): the **eye is `OIF_VISIBLE`** (` OIF_VISIBLE|OIF_ACTIVE` -> ` OIF_ACTIVE`, one span, nothing else in the 17 MB file changed) and the **cursor arrow is `OIF_ACTIVE`** (` OIF_ACTIVE` -> ` `, selectable). TEd writes the flags with a leading space, `|` between and always in the order VISIBLE, ACTIVE, DRAGGABLE; none set is a single space. The property grid of a layer lists three check boxes, visible / active / draggable (`OIF_DRAGGABLE`: what it does for instances is not probed). Re-saving an untouched tile in TEd reproduces `tile.ted` byte for byte; it rewrites the height map (the pixels differ by quantisation, -1 on 21,120 of 147,456 samples) and the blend / ground / protection maps, the river splines, and runs the stage A export (`working_data/.../building_list.xml`, same numbers as the shipped one to 0.5 mm) and updates `tile_database.bin` when a tile it did not know is loaded.
- **TEd hides what the file says is hidden**: osgiliath_test has Walls, Fort_Logic, rivers, Barricades, fields, streets and the Escalation layers hidden (`flags=" OIF_ACTIVE"` or `" "`), only Buildings and Gondorian Buildings visible. The tool drew all of them until Phase 1.
- **Placement modes, measured in TEd** (2026-10-10, probe copy of `tdd_custom_lothlorien/1x1/aa` loaded through File > Load Tile, edited in the Property Editor's grid, saved with File > Save Tile, the saved `tile.ted` compared instance by instance; 17 buildings, 63,153 vegetation instances):
  - The grid's `surface_mode` combo has two entries, **`Landscape: Above`** (`MSM_LANDSCAPE`) and **`Freeform`** (`MSM_FREEFORM`); a building's grid shows position (x, y, z), orientation (three angles), key, opacity, dirt_level, bounds_colour, burn, burn_amount, glow_amount, destruction_level, building_tech_level, indestructible, toggleable, capture_location and the three flag check boxes. `lf_offset` is not in the grid.
  - Landscape to Freeform: only `surface_mode` changes in the file, x / y / z stay.
  - **Landscape instance, x or z typed: y follows the terrain at once** (x 42.17 -> 90, y 1.9648 -> 11.8848, the terrain height at the new place). **y typed on a landscape instance is refused** (25 jumps back to the terrain height).
  - Freeform: y can be typed (25 stays). Switching that instance back to Landscape leaves 25 in the grid but **the saved file has the terrain height** (10.032401, the old value): a landscape instance is written snapped to the terrain.
  - **A changed terrain moves every landscape instance on the next save**: the height map of the probe was raised by 3000 raw (2.29 m; 3000 / 65535 x scale) on disk, the tile reloaded (File > Reload Tile) and saved: all 15 landscape buildings and 920 landscape vegetation instances got a new y (up to +2.24 m; the rest sit where the pixels saturate at 65535 or outside the map), the two freeform buildings, decals, layers, splines and polygons did not change, and the camera (a landscape item too) moved by +2.26 m. Right after the reload the grid still showed the old y: the re-snap is done when the tile is written (or lazily), not at load.
  - A plain re-save of an untouched tile moves 142 vegetation instances and 5 buildings by at most 0.7 mm: the re-quantised height map (-1 raw = 0.76 mm) followed by the re-snap. So **shipped landscape instances that are more than a few mm off the height map (the 6 % off by 5 cm to 5 m, the five TDD tiles) were saved with another terrain or another `min_height` / `scale`** than the files beside them; TEd would move them on its next save.
  - **The file's y of a landscape instance can be stale, and the tool shows it on the terrain anyway** (2026-10-10, bug report: buildings floating / under the ground in the Tile browser while TEd shows them right). In `tdd_settlement_dunedain_cities/dunedain_city_a/minor` 20,448 landscape buildings sit 5 m (median) under the terrain of `height_map_0.png` + the entry's `min_height -12.26 / scale 24.55`; their y matches BOB's `final_heights.dds` (-14 .. 3.75, BOB output, not used by TEd) to 0.08 m, i.e. they were snapped when the entry still had other numbers (png raw -> metres fits min -14 / scale 17.75). Same family: `tdd_custom_lothlorien/*` (vegetation y = 0), dwarven / elven / easterling cities. TEd re-snaps landscape instances against the current map and entry, so the tool does too: `TileDocument::snap_landscape_world` sets the world y of landscape leaf instances (buildings, vegetation, decals, VFX, ...; not polygons and splines, which carry their own heights) in the element index. The scene text keeps the file's y until the instance is edited; `Snap to terrain` / Freeform -> Landscape write the shown height, Landscape -> Freeform keeps the shown height. `tile_dump_placement <tsv>` and `tile_report_off_terrain` (by type) show the file/terrain differences.
  - The 3D viewport of TEd renders white to a screen capture on this machine, so brush strokes and mouse placement could not be probed; the grid and the saved file were enough for the rules above.
  - **The entry's min_height / scale can be stale against the baked terrain** (2026-10-17, second look at the floating / sinking buildings; Rust tool). The first fix only snapped landscape leaves; the freeform buildings (walls, nested groups) kept their file y against a terrain that was 5 m off, in `dunedain_city_a` 6.2 m median. BOB's `final_heights.dds` (R32F metres, `extent + 1` samples per side over the tile WITHOUT the border, sample (i, j) at x = i * extent / n, z = j * extent / n, no flip) fits the height map's raw values exactly with another min / scale in 5 of 1,039 battle tiles and none of 544 campaign tiles: `dunedain_city_a` minor / small / medium (-14 / 17.75, 18, 18 against entry -12.26 / 24.55, -12.39 / 27.39, -12 / 25.23), `farm_western/8x8/ac`, `wildmen_city_b/minor`. `TileProject::calibrate_from_final_heights` (`fit_baked_heights`: RANSAC line through (map metres, baked metres), at least 60 % of the samples within 5 cm, a relief of 0.5 m, clearly better than the entry) uses those numbers; the UI shows both. Not applied: the bake of every other tile is about 1.2 % lower than its entry (scale 900 -> 889, 20 -> 19.76) while its buildings follow the entry, so a change under 3 % of the scale is ignored. `cargo run --release -p wce_tile --example height_calibration_check -- <kit>/raw_data/terrain/tiles` lists the tiles.
  - **Instance heights, settled by the game's own data and TEd's code** (2026-10-17, the floating / sinking buildings; supersedes the "TEd re-snaps landscape instances on opening" guess above). (1) The game places a building at the y of its `building_list` entry as it is: `BATTLEFIELD_BUILDING::m_position.y` goes into `BUILDING` unchanged (`MANAGER::add_building` -> `BUILDING::BUILDING(..., height)`); `position_type` (relative 0 / absolute 1 / lf_relative 2) is only read and written by the list's (de)serialiser. In the shipped `tdd_pack2_battles` building list of `dunedain_city_a/medium`, 29,680 of 29,680 buildings (landscape and freeform) have exactly the file's world y (z mirrored about the 1,024 m tile). (2) TEd (`Ted::BASE_3D_INSTANCE`, Base3DInstance.h) keeps `position`, `surface_mode` (0 = `MSM_LANDSCAPE` "Landscape: Above", 1 = `MSM_FREEFORM`) and `lf_offset` as plain properties, saves them as they are (`FUN_00510010` writes the property list) and re-evaluates a landscape instance only on a terrain-changed event of its rectangle (a brush stroke, a reload of a changed height map); a fresh TEd save leaves 18 % of osgiliath minor's landscape buildings off the terrain (median 0, 90th percentile 0.33 m, 99th 1.6 m). So landscape and freeform buildings are both shown at the file's y; the tool no longer snaps them. Trees and decals (`VEGETATION_INSTANCE`, `ProjectedDecalInstance`) are generated onto the terrain by BOB from the tile's seeds (`modules`: `generation_seed`, `decal_generation_seed`), their y in the file is a leftover (0 in every lothlorien tree), so those leaves (and only those) are shown on the terrain. (3) TEd's height numbers: on save `normalize_terrain_section` (TerrainIO.cpp) stretches the section to 0..65535 and the tile database variation gets min_height / scale of the range; on load `denormalize_terrain_section` turns the png back with the variation's numbers. A stale variation (the entry edited after the last placing) puts the terrain off the buildings; the tool then takes the numbers the buildings were placed with (`calibrate_from_final_heights`, else `calibrate_from_instances`, both through `fit_baked_heights`). `lf_offset` is vestigial: 0 everywhere in TDD tiles, equal to the world y in CA tiles (town_greek_plains: 100 % of landscape and freeform instances). Checked on the four tiles with a stale entry that have buildings (dunedain_city_a minor / medium, farm_western/8x8/ac, wildmen_city_b/minor): 0 % of the landscape buildings within 5 cm of the terrain with the entry's numbers, 82 to 100 % with the fitted ones.
  - **The real cause of most floating / sunk buildings: the RMV2 mesh pivot** (2026-10-17, from the user's TEd screenshot of osgiliath minor: dome_of_stars stood 50 m too low). The half-float vertex positions of every rigid mesh are stored relative to the mesh's pivot (`Material::v_pivot`, at material header +0x224; always equal to the centre of the mesh header's bounding box, vertices centred on it: dome_of_stars raw y -48.7..48.7, header y -0.16..97.2, pivot y 48.53; checked on 10 vanilla and TDD models). The mesh is drawn at `vertex + pivot`, so a model's base stands at the instance's y. The renderer had `GpuMesh::offset` only for terrain patches and drew every building with its pivot missing: half its height under the ground, or floating when the pivot is below the origin (villa_stables: pivot y -5). Now `model_cache` sets `offset = pivot` and the mesh bounds include it. Still not drawn (shown as boxes): meshes of RS_TERRAIN_BLEND_V5 (the gaul_ / attila_ rocks, flag 86) and RS_STANDARD_AMBIENT_V5 (flag 64, e.g. gondorean_reskin_new_1).
  - **Terrain-blend meshes (RS_TERRAIN_BLEND_V5, the rocks), 2026-10-17.** Standard 32 byte vertices (rpfm_lib decoded them as 2 x f32[4]: positions of thousands of metres; fixed in `rpfm_wce_formats` `vertices/mod.rs` for version <= 6), the vertex colour alpha is the blend factor. The game's `RIGID_TERRAIN_BLEND_SHADER` (constructor fn 0x116ea1e0): `vs30_main` + `ps30_gbuffer` (`custom_geometry`, pass 0x3a), `vs30_geom` + `ps30_geom` (`geometry_30`: view-space depth like the terrain's `ps_depth`), `vs30_main` + `ps_terrain_material` (`custom_material`: the mesh's diffuse / normal added to the terrain accumulation with the weight 10 x alpha), `vs30_shadow` + `ps30_shadow`. The tool: the meshes are drawn in the G-buffer pass with stencil 2, the blend boxes read the G-buffer depth channel (so they project the terrain onto the meshes), the view depth and the material are added in the terrain pass before the resolve (`renderer/blend_mesh.rs`). The order is inferred from the shaders, not from the engine's draw order.

## Property Editor (TEd's grid), read from TEd.AssemblyKit.exe and QtToolUtility.AssemblyKit.dll (2026-10-17)
Every instance class of TEd (`Ted::BUILDING_INSTANCE` ...) is a reflected class: a static name table per class (parent properties first, `BASE_3D_INSTANCE`: `flags`, `surface_mode`, `position`, `orientation`, `behaviour_delegate`), a type per property, a `property_flags` function and `get_property` / `set_property` switches. The names of the tables are the attributes of the file (the 18 instance classes that have a tag of their own have exactly the attributes TEd names, plus `name` and `lf_offset`, which are not properties); a property whose type has no editor widget is not in the grid (`behaviour_delegate`, mesh handles, `selected_point`). `QTU::PropertyBagEditorBase::set_property_bag` builds the grid: `property_flags & 8` hides a row, `& 1` (and `& 2`) disables it.
- **Types and widgets** (`QTU::PropertyBagEditorBase`'s switch on the type id): bool = check box; `float` ranged `[0, 1]` (`TRANGED_VALUE<float>`: the type of opacity, dirt_level, burn_amount, glow_amount, layer_opacity) = `DoubleBoxSlider` (a number box and a slider); other ranged floats are `[0, 5]` colour_scale, `[0, 1000]` and `[0, 100]` (point light radius, colour_min, random_offset, subdivision_length, rank_distance, zone_skirt_distance, SPHERE radius), `[1, 100]` step_size, angles `[0, 2 pi]` (flag_facing, facing_direction: stored in radians, shown in degrees), plain float (parallax_scale, VFX scale); ranged ints (`max_subdivisions`, `min_num_players`, `rank_count`, `deployment_zone_id` `[0, 100]`, `alliance_id` `[0, 1]`) = `IntBoxSlider`; `destruction_level` = `TDYNAMIC_RANGED_VALUE<int>`, `[0, building->num_destruction_levels() - 1]` (the highest `destructNN` of the building's piece files; the range follows a changed `key`; the value of an instance above the range is shown clamped, as TEd's ranged value does: 6 of the 54 `gondorean_reskin_villa_house01` of osgiliath minor have 2 against 2 levels); colour = `ColourButton` (`argb(r,g,b,a)`: written with one decimal at least, `argb(1.0,0.0,0.0,1.0)`); vec3 = three number boxes (position, scale); `seasons` = four check boxes (` SEASON_BF_WINTER|SEASON_BF_SPRING|SEASON_BF_SUMMER|SEASON_BF_AUTUMN`, a leading space, in that order); `flags` = three check boxes (visible, active, draggable); strings = line edit (the edit is applied when it ends); enums = combo box over TEd's own tables (display name / file name pairs: the tables are in `wce_tile::property_enums`, 19 of them: export type "Export / Don't Export / Export Separately / Escalation 1-3", the polygon shapes "Circle / Semicircle / Rectangle / Polygon", the 41 AI hint types, the deployment zone types, the tech levels "Tech level 1-5", the zone purposes "Low wall / High wall / ...", ...); a command (`recenter_polygon`, `flatten`, `add_boundary`, `add_polygon`, `select_bmd`) = push button.
- **Rules** (`property_flags`): a layer shows `flags`, `position`, `export_type` (and a disabled `layer_opacity`); the polygon family shows `polygon_shape`, `orientation` and `area` disabled, `radius` only for a circle or semicircle; `ZONE_POLYGON_INSTANCE::locked` is disabled while the zone is in use; `BUILDING_INSTANCE`: `weak_wall` and `ai_breachable` only for a building of the category `fort_wall`, `dockable` for `fort_wall` and `unbreachable_fort_wall` (`this + 0x218` is the category of the `battlefield_buildings` row: `fort_wall` 0x14, `unbreachable_fort_wall` 0x1d). The files agree: of 3.7 M buildings in the kit, `weak_wall` / `ai_breachable` are in exactly the `fort_wall` instances, `dockable` in those and the `unbreachable_fort_wall` ones, `capture_location` only when it is not empty, `toggleable` missing in the oldest tiles. The category comes from the kit's `raw_data/db/battlefield_buildings.xml` (+ `TWaD_battlefield_buildings.xml`), which does not hold the TDD pack's own buildings: for those the grid shows the three rows when the instance has the attribute in the file. A new property of an element is added at the end of its attributes (TEd's order is a hash order; nothing reads it).
- **Building pieces**: when a building is loaded TEd creates a child instance per mesh (`BUILDING_PIECE_INSTANCE`, named "building piece"; buildings with doors / windows get "Doors" / "Windows" instance groups with their own children) and applies the building's properties to them (opacity, dirt_level, bounds_colour, burn, burn_amount, glow_amount, destruction_level go through `Ted::BUILDING_INSTANCE::set_property` to every piece). The pieces are not saved: no BUILDING_INSTANCE has children in any tile.ted. A piece's grid: flags (visible, active, but not draggable), surface_mode (Freeform), position 0, orientation 0, scale 1, opacity 1, burn, burn_amount 0, glow_amount 0, dirt_level 0, bounds_colour, show_collision, seasons (all), destruction_level (default: the highest level, the intact `destruct01`: in the kit's tiles most instances have `levels - 1`, and the fort walls of osgiliath minor, 37 of 37, have 2 with 3 levels; so level k shows `destruct0{levels - k}`, an unverified reading of TEd's piece code, `FUN_00420060`).
- **The tool**: `wce_tile::properties` (the schema per tag: kind, range, rule, twin attribute), `TileDocument::inspect_item` (one row per property in TEd's order; attributes the grid does not show are listed read-only below), `TedAttrCommand` (undo puts the old text back; the steps of a drag merge), the pieces as outliner children with the session-only `PieceProps` (position, orientation, scale, visible and destruction level are drawn; opacity / burn / glow / dirt / seasons are stored and not drawn: the game's per-instance parameters for them are not decoded). Script commands: `tile_inspect <elem> [piece]` (the rows with values), `tile_edit <elem> [piece <n>] <row> <value>` (one edit as the panel would make it). Not done: the push-button commands, the points of a river spline (`SplineRiverPoint`: terrain_offset, width, alpha_fade, flow_speed, foam_amount), the Doors / Windows groups of a building, the list selectors (`vfx`, `database_type`, `civilian_*`: plain text here).
