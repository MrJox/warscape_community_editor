# The editor shell (`libs/editor`, `app/`)

`wce.exe` is one window with one renderer and one shared scene; tools are modes of it. Phase 4 built the shell, Phase 5 moved the Weather tool onto it
(`tools/weather`, see below), Phase 6 the Tile tool, Phase 7 lets the tools share documents (see Cross-tool composition).

## Pieces

| Piece | File | What it does |
|---|---|---|
| `Command`, `CommandStack` | `editor/command.h` | undo/redo per document; a drag gesture pushes many commands with one merge key and ends as one entry (`break_merge` when the gesture ends); `modified()` follows the saved position |
| `Document` | `editor/document.h` | one thing a tool edits, with its lossless model inside: `publish` into its scene layer, `outline`, `inspect`, `item_transform` / `transform_items` for the gizmo, `save` |
| `DocumentManager` | `editor/document_manager.h` | owns the open documents, one `RenderScene` layer each, re-publishes a document when its stack moved; `unsaved`, `save_one`, `save_all`, layer visibility, the stand-in scene rule |
| `Selection` | `editor/selection.h` | a set of `SourceRef` (document, item); the scene entities that show them come from `RenderScene::entities_of` |
| `Inspector` | `editor/inspector.h` | the documents describe an item through this interface; every property has a `PropertyPath` (document, item, field), the seam the Cinematic editor animates through; `panels.cpp` has the ImGui implementation |
| opening what is open | `editor/editor.rs` (`open_path_with`) | a document is not opened twice: a pack file whose `source_key` is open, or a disk path a document says it came from (`Document::opened_from`: a tile's folder, any file in it, its entry, or the kit's folder whose project it is) activates the open document |
| `CommandRegistry`, `ScriptRunner` | `editor/command_registry.h` | every action is a named command; menus, `--cmd`, `--script` and tests all run the same entries |
| `TotalWarCamera`, `TopDownCamera`, `WalkCamera`, `FlyCamera`, `OrbitCamera` | `wce_editor_core::camera_controller` | viewport cameras on the game's battle lens (FOV 65 degrees, near 1, far 13000); the top-down view is orthographic. The ground and the models' bounding boxes they keep out of: `wce_editor::camera_world` |
| `Viewport` | `editor/editor.h`, `viewport.cpp` | renders the scene into a `RenderTarget`, camera input, click to select (through `Renderer::pick`), the ImGuizmo gizmo (translate/rotate/scale, snap), offscreen `capture` |
| panels | `editor/panels.cpp` | Inspector, Assets (the VFS tree, filter, only the tool's file types, double-click opens), Log, History (click to jump), Commands (console) |
| `Editor` | `editor/editor.h` | the host window with menu bar, tool switcher and dockspace; owns VFS, renderer, scene, documents, selection, clock; layouts; first run |
| `Tool` | `editor/tool.h` | a mode: opens, panels, menus, viewport input, default layout, commands; `PlaceholderTool` for the future ones |

`libs/editor` is two targets: `wce_editor_core` has no ImGui or GPU code and is what `cli/editor_check` tests; `wce_editor` is the UI.

## Tools

Registered by `app/main.cpp` through `tools/tool_factories.h`: Weather (Phase 5), Tile, Unit, VFX, Terrain, Cinematic (placeholders with a
panel that says what is planned). **Ctrl+1..9** switch tools.

To add a tool: derive from `Tool`, give it an id and title, return the file extensions it opens, implement `open` (return a `Document`), add panels in
`draw_panels`, commands in `register_commands`; add a factory to `tool_factories.h` and register it in `main.cpp`.

## Weather tool (`tools/weather`)

Opens `.environment`, `.lighting` and `.xml` (weather definitions, vfx) from the packs or from disk (File > Open file, `--open`, `--open-disk`, double-click in Files). Each file is an
`XmlFileDocument` around the lossless `XmlDoc`: attribute edits are `XmlAttrCommand`s (merge per drag gesture), structural edits (duplicate, delete, move, add child or attribute,
remove attribute) are snapshot commands. Save writes a file of the packs as a loose file into the project's loose folder (`<projects>/loose/<its path in the packs>`, `Editor::loose_path`; the game's `data` folder is never touched; see [Saving and exporting](#saving-and-exporting)), re-reads it as
the new baseline and clears the history, so the saved bytes differ from the pack file in the edited spans only.

The **Inspector** of an `.environment` / `.lighting` file groups its settings by effect (Sun, Ambient light, Sky, Fog, Exposure and tone mapping, Colour grading, Depth of field, Water, Wind and snow, Precipitation node, one Cloud layer per plane, then Other attributes), each with a tooltip (`wce_weather::environment_sections`, `Tool::inspect` of the weather tool; the Properties tab keeps the raw XML tree for everything else). A setting the file lacks shows dim at the value the viewport assumes (`EnvironmentParams::default`) and is added to its element (`Op::AddAttr`) when edited; a number the file writes as an integer stays one while it is whole. Attributes of these elements that no section lists, like the single `low_tones_bias` the battle game ignores, are under Other attributes. A missing element (a `.lighting` has no `SKYGEN`) is not added.

| Old weather_editor feature (`docs/plans/weather_current_state.md`) | Where it is now |
|---|---|
| Files browser with filter and categories | **Files** panel (and the shared Assets panel, filtered to the tool's types) |
| Properties tree with typed editors, search, per-attribute revert, add / remove | **Properties** panel (tree) and the shared **Inspector** (typed editors for bool, int, float, colour, variance, euler, string) |
| Structural edits with snapshot undo | context menu in Properties; `xml_op`; Ctrl+Z / Ctrl+Y, History panel |
| Changes tab | **Changes** tab of Properties (every modified attribute of the file, revert) |
| Live preview on the sample map, orbit camera, battle lens | shared viewport; the tool's environment document lights `RenderScene::environment` every frame (while the tool has a VFX or `weather_definitions.xml` file open instead, the last environment it had, as saved; a default dry environment when none) |
| View modes (HDR, albedo, normal, depth, ...) | **Weather scene** bar and `view <n>` |
| Sample map seed and count, re-roll | **Weather scene** bar, `sample`, `reroll` |
| Graphics options (gamma, brightness, SSAO, DOF, shadows, vignette, flare) | **Settings** menu (read from `preferences.script.txt`) |
| Weather selection database: Pick and Edit tabs (flag bits, categories and values with the game's locked unless Expert, clone a map / climate, coverage grid, conditions grid, problems for the game, undo), Open / Save / Save As / Convert `.xml` and `.bin` (docs/re/variation_db.md). A game without the database (`GameFeatures::variation_db`; Rome 2 picks by the weather folders) has the item disabled, with why | **Selection > Weather picker** (`WeatherPicker`, `VariationEditor`), `picker`, `pick k=v`, `vdb-script` |
| CLI `--open`, `--open-disk`, `--cam`, `--frames`, `--shot`, `--capture`, `--view`, `--blend`, `--pick`, `--picker`, `--vdb-script`, `--no-flare` | same flags of `wce.exe`; the weather ones are commands of the tool (`--name args` runs the command `name`) |

**Visual editing** (`visual.rs`, an `.environment` / `.lighting` file open): the **sun** is a disc in the sky of the viewport where the game draws it; dragging it puts the sun under the cursor, and **Ctrl+L** held over the viewport turns it with the mouse's motion (sideways the azimuth, up and down the elevation, 0 to 90; Unreal's shortcut). The angles are the file's (a tile's battle frame turn taken off), to a tenth of a degree, and one drag is one undo entry (`XmlFileDocument::edit_setting`, `join_last`). The **Weather scene** panel has *Compare with saved* (also **C** held over the viewport, `weather_compare on|off`: the file as saved, the project's loose copy or the packs', lights the scene instead of the edits, with a banner; exposure adapts across the flip as in the game), *Pick focus* (`weather_pick_focus`: the next click sets DOF_focus to the view depth of the surface under it; ASSUMPTION: the shaders compare it with view depth) and *Tone curve and histogram* (`weather_tone_panel on|off`: the per-channel S-curve of low_tones_bias / high_tones_bias as the engine bakes it, the frame's brightness histogram with the clipped and crushed share, read back twice a second only while open, and the adapted black and white points). `weather_sun_disc` says where the disc is, for scripted drags. The keys are in Settings > Shortcuts (Weather). The ideas not done yet: [plans/weather.md](plans/weather.md), Open 3.

Differences: the legacy app held one active file; here every open file is a document, and the one that lights the scene is the last active `.environment` / `.lighting`. `weather_editor.exe` was removed in Phase 8; the render regression is the `wce.exe` captures (`scripts/shots.sh`). `scripts/weather_check.sh` supersedes `variation_e2e.ps1`.

## Tile tool (`tools/tile`)

A tile's root is its tile database entry (`_tile_database/TILES/*.xml`, [formats/tile_database.md](formats/tile_database.md)): it names the folder of `tile.ted` (location + variation) and holds the size, colour, ground groups, height / normal parameters and links. Open one with the **Tiles** panel (the kits' entries from an index, no scan; word filter; double-click opens the first variation, a button per variation; above the list, **Favourites** (the star at a row's right, `tile_favourite <key>`) and **Recently opened** (the last 10 tiles opened, with the variation, which a double-click opens again), both of the panel's source and under the same kind and word filters, kept in `[tools.tile] favourites` / `recent` (`tile_marks` logs them); an exported tile opened into a workspace counts as the packs'), Tile > Open tile... (an entry `.xml`, a `tile.ted`), `--tile <target>` or the `tile <target> [variation]` command, where the target is an entry file, a name (`assembly_kit/osgiliath_test`, or the entry's file name), a variation folder, a tile folder (opens its first variation) or a `tile.ted`. A folder or `tile.ted` resolves its entry from the path; outside a kit there is none and the tile opens with a warning and no height scale. The **Tile** panel shows the entry read-only (colour, size, flags, ground groups, a variation chooser that opens the other variation in this one's place, the variations' height / normal / overlap values, links and targets). A `TileDocument` wraps a `TileProject` (the lossless `TedScene` and the `HeightField`), and everything it does is a `Command` on the document's stack:
attribute edits on the scene (moves, rotations, polygon points) merge per gesture, structural edits (duplicate, delete, add building, polygons, layers) keep whole-document snapshots, and a brush stroke is one entry however many steps it took. Items are element indices + 1 (item 0 is the terrain), so the shared
selection, inspector, gizmo and history work on them.

**Problems** (`wce_tile::vegetation::trees_outside_exclusions`): BOB keeps a manual `VEGETATION_INSTANCE` only when it stands inside a `VegetationExclusionPolygonInstance` (none when the tile has no such polygon), so the others never reach the game. They are listed in the Tile panel's *Problems* (a click selects and frames one; `tile_problems` logs them), an error in the log when the tile opens, and a warning at the front of every save's message.

**Where tiles are saved** (`wce_tile::project_files`, `tile_document/kit.rs`): a tile is saved as **`tile.wce`** in the game's projects folder (`<projects>/assembly_kit`, laid out like a kit's `raw_data`: the tile at `raw_data/terrain/tiles/...` and its entry in `_tile_database/TILES`), never in the Assembly Kit. `tile.wce` is a superset of `tile.ted`: the same XML, the root `<project>` marked `wce_version="1"`, where the editor may keep what TEd does not know, named so that the conversion finds it: an attribute `wce_...`, an element `Wce...`. Numbers are kept at full precision (`format_number`: positions, orientations, points, handles, areas); TEd's precision is applied only by the conversion (`ted_number_text`: `%.6f` of the float32 trimmed, `%g` for points, handles and `lf_offset`, integers as they are, only where that is shorter, so what TEd wrote stays byte for byte: 2 of the kit's 39.9 million values would differ, `examples/ted_numbers_check.rs`). A placed prefab is a **reference**: an instance group with `wce_prefab="<key>"`, kept in tile.wce without its contents; the editor fills them in from the prefab when it opens the tile (`expand_prefabs`, prefabs placed in prefabs too) and leaves them out when it saves (`strip_prefab_contents`), so an edit of the prefab reaches every tile that places it. The conversion for TEd (and for the game export, which compiles the editor's scene) writes the group with its contents: TEd's copy. The first save of a tile opened from the kit makes its project (the tile's folder and its entry copied, `tile.wce` written) and the document goes on from there; opening a kit's tile that has a project opens the project. A project's entry lists every variation, but a variation is in the project only once it was saved: one that is not opens from the kit's copy (an extracted tile's is extracted from the packs, the entry keeping the other variations' numbers), and its first save brings it in, leaving the project's entry as it is (a save changes only its own variation's `min_height` / `scale` in the entry file). Save writes only what changed (the edited spans, the kit-exact PNG encoder for the height map, the river files of rivers that changed); `save_to <folder>` writes the tile elsewhere. **File > Export > For Assembly Kit** (`save_for_kit [raw_data]`) writes a tile TEd reads into the kit that has the tile's kind: `tile.ted` (`project_files::to_ted`: the polyfills of the editor's features, then what TEd lacks dropped, all in the log), every river file, the height map, the other files and the entry; files with other bytes keep a `.bak`, identical ones are left alone. **Tile > Import from Assembly Kit** (`import_from_kit`) opens the kit's copy of the project, whose next save replaces the project. A tile **extracted** from the packs (`open_exported`) is decompiled into the projects at its own folder, the kit's tile of that name and it sharing the project, and its `tile.wce` is marked `wce_extracted_tile="true"` (`project_files::EXTRACTED_ATTR`, dropped silently for TEd and the game; the Tiles panel shows a package on its row). Extracting a tile whose variation folder has a project already asks first (`extract_prompt.rs`): **Open the project**, **Overwrite** (the variation folder replaced; the entry keeps the other variations' numbers) or **Cancel**; `open_exported <folder>` opens the project, `--fresh` extracts over it. **Import from Assembly Kit** on an extracted tile extracts it again from the game. Projects of older versions kept extracted tiles at `<tile>_extracted` folders and locations: **Tile > Migrate old extracted projects** (`migrate_extracted`) moves them to their own names and marks them, leaving any whose place has a project, or that is open, as it is (listed in the log).

**Several Assembly Kits** (Settings > Game, `GameSettings::assembly_kits`; `WCE_ASSEMBLY_KIT` is a `;` list): one list is the single place that says where the kits are, `Settings::assembly_kit_dirs` / `assembly_kit_raw_dirs` (a development install's battle tile map kit brings the campaign one; with no list the kit in the game folder is used). The Tiles panel lists each kit's tiles (a kit whose folder name another shares is named by its whole path), the prefab library reads every kit's `art/prefabs`, and where a tile or prefab is in several kits the first of the list wins (Import from Assembly Kit, opening a variation the project does not have yet). "Save for Assembly Kit" asks which kit when several fit (`kit_prompt.rs`; the `save_for_kit` and `prefab_save_kit` commands take the first, or a raw_data folder). The old single `assembly_kit` setting is moved into the list when the file loads.

**Launch in game** (`launch.rs`, `launch_prompt.rs`; [plans/launch_in_game.md](plans/launch_in_game.md), the command line in [re/game_command_line.md](re/game_command_line.md)): **Tile > Launch in game** (`tile_launch_game [--dry-run] [--ignore-movie-packs] [--async]`) exports the open battle tile, writes a battle XML (`script/wce/wce_launch.xml`) and starts the game with `show_frontend_movies false; game_startup_mode battle script/wce/wce_launch.xml;`: the game goes straight into a battle on the tile; `used_mods.txt` is not touched. The work runs on a thread behind a progress window: the steps (the game's tile data the first time, the compile, the packs the tile needs, the launch's files, the start), what the step going on is doing (`wce_foundation::activity`: each compile stage, each climate's trees and props, the grass, the dependency scans, with their times), the time taken and the time left from the last launch's steps (`[tools.tile] launch.step_seconds`), Cancel. **Delivery** (Settings > Tile, *Launch in game*): *launch pack* (default, below) or *loose files*, written under the launch's folder (`<projects>/build/launch/<id>/game`, `Editor::build_dir`) and given as `add_working_directory`, with only the mod packs chosen in the editor that the tile needs (`launch::needs`: the buildings' `rigidmodels/buildings/<key>/` files, every asset path in the shipped files and in turn in the models and definitions they name, the climate's ground textures and grass, the weather file, the pack each is read from; the mod packs whose `models_building`, `main_units`, `land_units` or `factions` tables hold a key the release's tables lack); the game's packs win over loose files (the release's too: `tiles.pack` has the tile database), so a pack that loads with a path the tile ships, a tile with procedural walls (their database rows) or no mounted files make that launch use the pack, with the reason in the log: in practice every tile. *Launch pack*: `data\wce_launch.pack` (a mod pack with a marker) named first, then every mod pack chosen in the editor. Files the tile uses from the editor's loose folders (an edited weather file) go along either way. The battle: the tile alone as the map (its variation folder; `land_normal`, the playable area and deployment scaled from the tile's size; a tile with deployment zones gives each army the zone of its `deployment_area_alliance_index`, the defender's inside the walls, the attacker's ring, and puts its unit in it, `launch::Zone`), or the Map context's placement in the game's campaign map (`tile_map_position` = the placement's centre cell / the map's size, y from the top; `settlement_standard` and the *Tile upgrades* for a settlement tile set; the kit's maps are not in the game's packs, so they fall back to the tile alone); the tile's weather; one unit a side, the current game's (`[games.<id>.tools.tile] launch_army`; an empty key is the game's vanilla one, `GameProfile::launch`), and the elements its engine lacks left out (Rome 2: the alliances' indices, the tile upgrades). The game's executable, data folder, pack format and campaign map are its profile's; a launch being prepared or a launched game keeps its own game when the editor switches to another. **Linux** (`proton.rs`): a game folder with the game's executable is the Windows build, started through Proton as Steam starts it: the compatibility tool Steam runs the game with (`config/config.vdf`'s `CompatToolMapping`, the game's app id, else the default; a custom tool of `compatibilitytools.d`, or Valve's folder in `steamapps/common` whose name reads as it), or the Proton folder of Settings > Tile (*Proton*); inside the Steam Linux Runtime its `toolmanifest.vdf` requires (each tool's `commandline`, verb `waitforexitandrun`), in the game's prefix `steamapps/compatdata/<app id>` (made by Steam at the game's first start). Wine quotes and escapes every `"` of a program's arguments, so the command line goes into `wce_launch.bat` in the launch's folder, run by the prefix's `cmd`; a loose launch's working directory is `Z:` + its path. The game does not inherit the editor's own DXVK-native settings (`proton::EDITOR_ONLY_ENV`: `DXVK_WSI_DRIVER`, `DXVK_LOG_PATH`): Proton's DXVK reads them too, and with `DXVK_WSI_DRIVER=SDL3` Attila crashed while a battle loaded (`Empire.Retail.dll+0x178c1b6`). A folder without the executable is a native Linux build, which is not launched. The process checks read `/proc` (Steam is its `steam` client). Before the start: the game must not be running, Steam must be, and a movie-type pack in `data\` that is neither the game's nor `@wce_proc_data.pack` opens a question (*Launch anyway*). The tool waits for the game (its `update`) and removes the launch's folder and pack when it exits; the other launches' folders go only when no game runs (a dry run clears only dry runs' `d...` folders); what an editor closed meanwhile left is removed at its next start. `--dry-run` does everything but the game; `--async` runs as the menu does.

**Fixes menu** (`wce_editor::fixes`; a tool offers them with `Tool::fixes`; `fix list|open|apply|remove <id>`): one-time repairs of the game, not of a document, shown for the games they apply to, ticked when installed. Each opens a window that says what it does before anything is written, works on a thread, and can take out what it wrote. Its packs go at the head of the mod list, ahead of the mods they were built from, and are left out of what it reads, so building again does not patch its own work. **Light wall torches** (Attila, `wce_tile_editor::building_effects`, docs/re/buildings.md): the two packs that make wall torches and the lighthouse burn, built from the game and the chosen mods; the movie pack is one of the editor's own for Launch in game's check of stray packs.

**Terrain layers** (`wce_tile::terrain_layers`, the Tile panel's section, `terrain_layer`; [plans/procedural_roads.md](plans/procedural_roads.md)): height, texture and ground type maps made by composition, as the newer Terry's. What is painted goes into the working layer, whatever the tool, and the base stays as it was. They live in `terrain_layers.wcl` beside the tile; the tile's maps hold what they make, which is what Save for Assembly Kit writes. A layer can export only with a scene layer ("Exports with"; the scene layer gets a `wce_layer_id`): Save for Assembly Kit and the game export (`TileProject::export_maps`, through `save_exported_with`) leave it out while that layer is "Don't Export". An escalation layer has no terrain of its own (its BMD holds buildings, props, effects, capture points, no-go regions and zones), so a layer depending on one exports with the tile at every level, and the panel says so. A hidden working layer takes the paint without showing it, and the panel warns. Everything undoes, the stack's own changes too.

**Procedural roads** (`WceRoadSpline`, Create panel with the roads; `wce_tile::roads`, `tile_document/roads.rs`; [plans/procedural_roads.md](plans/procedural_roads.md)): a line whose road is generated: the ground under it smoothed to a maximum grade, banks that widen to hold a maximum side slope, a texture and a ground type, each in a layer the road owns, made again when the road or the ground under it changes; its road type's pieces laid along it, end to end, bent to it by overrides (`wce_tile::road_layout`: straights, curves, a corner on each sharp point, `road_sharp` or the Polygon panel's checkbox, an end piece on each free end, fences along either side and round its corners and junctions when `road_fences` asks for them, tilted to the ground, `road_fence_damage` of them destroyed; a road's end within 8 m of another road is taken onto it and makes a T junction there, two roads crossing an X junction), fords over water less than 0.75 m deep (the road on the bed, the terrain's heights left alone, ford pieces), and bridges over deeper water (their deck `road_bridge_clearance` over it, the road climbing to it) and over drops, generated too: a kit bridge (`road_bridge`: wood or stone) bent along the road, widened to it, its posts down to the ground (`wce_walls::bridge`); an export makes them as walls are made, into the same packs. Each bridge and ford gets an `AIH_BRIDGE_CROSSING` hint in an export, as vanilla's crossings have; `tile_export_text <file>` writes the scene as an export reads it. Roads and walls are made off the editor's thread (`tile_document/jobs.rs`), put in place when they are done; `tile_wait_jobs` waits for them (scripts), and an export waits for the roads. TEd never sees the element; an export writes the terrain it makes and its instances as the layer *WCE procedural roads*. **Road pieces** (`wce_tile::road_pieces`, being redesigned): prefabs in the projects' `art/prefabs/roads_proc/<type>/`, keyed `road_<type>_<piece>`; the placeholders of `roads_proc/base/` (guides only) are written when the prefab library is first scanned for a game, where missing or an older generation nobody edited (`wce_generated`), and so is the first road type, `roads_proc/dirt` (`wce_tile::road_dirt`), made of the kit's road decals when its `global_dirt_road_*` prefabs have them. A piece marks its road with `WceRoadGuide` lines (`guide_role` centre, edge, verge or port), shown on the Prefab tool's stage only and dropped by every save for TEd; a part's own `road_anchor` (surface, edge, verge, fixed) overrides where it stands.

**Export as prop** (`wce_tile::export_as_prop`, a checkbox of a building in the Inspector, kept in tile.wce as `wce_export_as_prop`; newer games' tools have it, Attila's TEd does not): the building stays a building in the editor, and an export writes it as plain models, one `SIMPLE_MESH_INSTANCE` per piece at the building's place, scale and destruction level (the game ignores a building's scale, so the Inspector's **scale** row and the Scale gizmo work on a building only while it exports as a prop; off again the value is kept and greyed out, and the viewport draws scale 1, as the game does; docs/re/buildings.md), so that it has no collision, destruction, effects or logic and leaves the building lists, the terrain stamps and the capture locations (`TileDocument::text_for_export`: the game export and Save for Assembly Kit read the same converted text; tile.wce keeps the building). A building with a `capture_location` has the checkbox greyed out, with a tooltip saying why (that one, with a piece that has no plain mesh (the siege engines), or without models in the mounted files stays a building, and the log says why). BOB takes every simple mesh for a water plane and stops at the first that is not one: the models' names end in `__wce_prop` and the editor's stage B leaves them out (`compile::water_planes`), so the water map does not change; TEd's own export has no such exception, and Save for Assembly Kit warns when water planes come after such a model. In a prefab: the box on an item of a placed copy is that copy's override, Edit prefab's is the prefab's and reaches every tile that places it; both convert when the tile is exported. Save prefab for Assembly Kit converts them too (`PrefabLibrary::save_for_kit`), as a tile's save does, and says in the log that a tile placing the prefab loses the water planes after those models in TEd's own export: the prefab cannot know them.

**New tile** (`wce_tile::new_tile`, `new_tile_dialog.rs`; the review of TEd's New Tile in [plans/workflow_review.md](plans/workflow_review.md)): **Tile > New tile...** asks for a name (no spaces, lower-cased), the size (1..64 cells a side, default 8), the terrain height (default 10, in the height map's units as TEd's: wce shows 5 m) and the density (32, 64 or 128; above 16 cells a side it drops to 32 unless chosen), shows the files' size, and writes a **project** at once: the entry `terrain/tiles/battle/_tile_database/TILES/assembly_kit_<name>.xml` (tile set `assembly_kit`, variation `battlefield`, TEd's flags, texture groups and colour, min_height = the height, scale 50) and in `terrain/tiles/battle/assembly_kit/<name>/battlefield` `tile.wce` (empty), a flat `height_map_0.png`, `blend_map.tif` (all the first texture group) and `ground_type_map.png`, each `(cells + 2) * density` pixels a side; then it opens. A name a project, the kit's raw_data or its working_data already has is refused. `tile_database.bin` is not touched (the export compiles it from the entries). Command `new_tile <name> [x] [y] [height] [density]`. **The height range follows the terrain**: the heights are kept in metres, so the brushes are not held to the entry's range; a save that writes the height map fits min_height / scale to its lowest and highest samples as TEd does (a flat map: scale 50; kept when within half a step of the old range, so an unedited map keeps its numbers) and writes them into the entry next to the saved tile (the message says the new range). Only a folder the entry points to (its location and the variation) gets the range: saved into another one (File > Save as elsewhere, a tile without an entry) the heights keep the range they are stored with unless they left it, no entry is written, and the message says the folder opens again without its height range, size and colour. **File > Save as** of a tile into a `battle/<set>/<name>/<variation>` folder of the projects is **Tile > Save tile as...** (a new tile with its own entry; `TileDocument::save_as_new_tile`).

What it shows: the terrain from the height map (patches of the shared terrain pass), BUILDING_INSTANCEs as their real models (`rigidmodels/buildings/<key>/` pieces; a key without a drawable model is a wire box and is listed in the log), every other instance as a small marker batched per type

A node's **Bounding Box** is read by the game as a rectangle (its first 4 points: any size, turned any way; its area is how many units the node holds): it is drawn as its first side's two corners and a point at its depth, made a true rectangle (`bounding_rectangle`; 4 points: the 4th is put right; 2, or more than 4: the box around them), as the Inspector says while it is drawn and under a node's buttons. **Placement** (Phase 2; the rules were measured in TEd, `docs/formats/tile_ted.md`): an instance is *Landscape* (`surface_mode="MSM_LANDSCAPE"`, TEd's `Landscape: Above`) or *Freeform*. **Building technology** (`tile_document/tech.rs`, `tech_chip.rs`; TEd's Building Settings): a chip at the viewport's top right, left of the ground views' (a dashed square, lit while something is drawn), opens a popup that picks what of the buildings' logic files (`<key>_tech.cs2.parsed`, read once per key through rpfm's `Cs2Parsed`) and their pieces' `.meta` files is drawn over them. Nothing is drawn until something is ticked (all off at the start, kept for the session only: a view setting of the tile like the polygons', not in `settings.toml`; the Game view hides it like the other overlays). The kinds, by group, each with a colour swatch and a tooltip: *Collision* (the collision mesh's triangle edges, gate collision, the hard outlines that block units, soft collision cylinders), *Walking and fighting* (the footprint outlines, platforms filled and coloured by flag, pipes by type, formation lines by action with their facing, docking lines), *Siege and effects* (arrow emitters, action effect nodes, attached buildings, the `.meta` particle emitters: bright when they play while the building stands, dim on events, a box for volumetric ones) and *Frames* (the bounding boxes, the minimap flag). **Buildings**: *In range* (every building within a range of the camera, 30..1000 m, the nearest first, at most 600 000 lines; drawn again when the camera moved a sixth of the range) or *Selected* (the selected buildings, or those in a selected layer or group); *Draw through the models* (on by default: the hulls are inside the models) turns the depth test off. **Checks**: *Overlapping buildings* (TEd's `detect_building_collisions`) outlines in red, with a pole above, the buildings whose footprints (the hard outlines, else the state's box) overlap, and joins each pair by a line; footprints that only touch (within 0.2 m) do not count, two on the same spot do, and a selection is tested against what stands near it; *Most destroyed state* (TEd's `force_show_highest_destruct_level`) draws every piece's last destruction state instead of the one the building shows (the models do not change). Footprints are laid on the ground (their files have no heights; the game lays them on the terrain), a point every unit, and drawn again when the heights change. **Procedural walls** are drawn as buildings too (user, 2026-11-04: to find their pathfinding and formation line bugs): their preview pieces' logic files, made with the pieces (the meshes' intact state), each piece at its frame; a wall is as far as its nearest piece, *Selected* takes a selected wall, the overlap check leaves them out (they stand against their towers), and a wall made again draws its new pieces (`scripts/tile_wall_tech.txt`); `wall_tech_check [gaps stacked loose]` checks the selected walls' pieces together in the world (stretches no footprint covers, platforms over one another, formation line ends on no platform; with numbers, a test). The state drawn is the instance's: its saved `destruction_level`, a piece's own (the Inspector), and a hidden piece draws nothing; a piece whose `show_collision` is ticked draws its collision whatever the chip says. ASSUMPTION: a soft collision's `point_1` is (radius, height); a docking line lies 0.2 above its piece's ground plane (no shipped Attila file has one). Commands: `tile_tech [all | none | on|off <kind>... | scope all|selected | range <m> | xray|highest|detect on|off | fill <0..1>]` (no argument logs the settings; kinds `collision gates outlines soft footprints platforms pipes formation docking arrows actionfx attached emitters bounds flag`), test `assert_tech <buildings> [min lines] [collisions n]`; `scripts/tile_tech.txt` (in `tile_check.sh`) and the gate `tech_check` (every logic file of the game reads into shapes).

**Procedural trees** (*Trees* in the ground chip, `tree_list [on | off | auto | <category>]`): generated by the editor as BOB would (`wce_tile::vegetation`) from the tile as it is: its seeds, edited height map, exclusion polygons, static trees, the blend map as painted (the saved `blend_map.tif` until it is loaded) and the Assembly Kit's vegetation parameters, for the ground's climate as the game picks it (the climate's own category when the kit has one, else `default`; `tree_list <category>` picks another, `auto` goes back). The packed tile's lists (`<list>.tree_list.bin`) are not drawn while the trees can be generated: a decompiled tile's generated trees came from seeds it does not have; without the kit's parameters
(Rome 2), outside a kit's `raw_data` or without `<Vegetation>` seeds, the climate's packed list (its own, else `default`; in the tile's
folder, the game files or `decompiled_vegetation/`) is drawn as shipped instead (the chip says so). They draw with the static `VEGETATION_INSTANCE`s, not selectable; a generated list holds the static trees too, and those standing where a static instance stands (shown or hidden) are skipped, so hiding the instances' layer hides those trees. The trees and the grass are generated again by themselves when what they are made from changes (`Tile::follow_vegetation_inputs`): the
heights, the painting, the seeds, the exclusion polygons, the static trees, the climate (the grass keeps its patches and takes the climate's
models); looked at when the history, heights, painting or climate move, done once nothing has moved for 0.4 s (a drag or a stroke: at its
end). *Regenerate* makes them again by hand. Generation runs on a thread of its own (`vegetation::Job`; the grass's too): what it reads of the tile (the heights, the painting, the seeds, the static trees) is taken on the UI thread, the generator runs there, and the trees and grass drawn stay until the new ones are done (0.01–0.1 s for most tiles, seconds for the largest: custom_mont_blanc, 51k trees; middle_men_port_a/minor, 32k trees and 700k grass patches). Placement as the game's (`docs/re/vegetation.md`): terrain height unless freeform, scale byte / 127, the game's random yaw for one worker, tilted to the terrain (static trees too). The static instances draw the model their key becomes on the trees' climate (`per_climate_tree_conversions.xml`: olives turn to oaks on ROME_Atlantic...), as the game's lists have them. Trees (and grass) draw their season's diffuse (`<name>_<season>_diffuse`, the ground's season) where the game has one.

A project decompiled before 2026-11-12 has one exclusion polygon over the whole tile (BOB generated nothing there); opening it replaces that polygon with polygons around its static trees (`tile_document::convert_whole_tile_exclusion`, docs/formats/tile_decompile.md) on
the project, before the document is made from it (so it draws from the start); the tile opens modified (no undo entry): save to keep it.

**Grass** (*Grass* in the ground chip, `grass on|off|regenerate`): generated as BOB would from the tile as it is: its `<Grass generation_seed>`, the blend map as painted (the saved `blend_map.tif` until it is loaded) and the kit's `max_grass.xml` (exact to BOB on 119 of 125 kit tiles); Made again by itself when the heights, the painting or the seed change (see *Procedural trees*); *Regenerate* by hand. The packed tile's `default.grass_list.bin` is drawn only when the grass can't be generated (no `max_grass.xml`: Rome 2; outside a kit's `raw_data`; no seed), as shipped (the chip says so): a decompiled tile's came from a seed it does not have, and it goes stale with the first edit of the heights or the painting. Drawn by the renderer's grass pass with the game's rigidgrass shaders, within 100 m of the camera (where the game's vertex shader has sunk it into the ground); models from the climate's `terrain/vegetation/battle/grass/<climate>/` folder, else `default`. Placement as the game's: on the terrain, tilted to its normal measured over the patch's size, patches on slopes over 0.7 rad left out, the game's random yaw for one worker; the season's diffuse (`<name>_<season>_diffuse`) where the climate has one; grass casts shadows.

**Tile links** (Phase 6a, read-only; `docs/re/tile_links.md`): the Tile panel's *Tile links* section is a map of the entry's link targets and rules (`links_editor.rs`: the tile's cells, the ring of neighbours' cells round them, a colour per link set; a click picks a link and moves the view along to its cell, at the height, angle and distance it had, or adds a target on the tile and a rule around it; a right click removes one) and *show on the ground* draws the cells they name coloured by link set. The tiles that can follow are looked for in the tile's own database over the projects', the kits' and the packs', mods included. Commands: `tile_links [on|off]` (no argument: log them); tests `assert_links <targets> <rules> [drawn 0|1]`, `assert_link_cell <x> <y> <x0 m> <z0 m>`.

Entry commands: `tiles [words]` (the browser's rows), `tile_entry` (log the entry), `assert_entry <field> <value>`, `assert_tiles <n> [words]`; test helpers `gizmo_drag <x|y|z> <pixels>` and `cam_info`. Extra commands: `tile_mode`, `brush`, `grab_to x z`, `tile_click`, `tile_click_ground`, `tile_drag_point`, `draw_polygon`, `tile_diagnostics` and the tests `assert_instances`, `assert_type_count`, `assert_world`, `assert_world_xz`, `assert_height`, `mark_height` / `assert_height_delta`, `assert_selected_type`,
`assert_at_cursor`, `assert_mode`, `assert_grabbing`, `assert_file_exists`. `mouse move|click|drag|wheel|off x y` (pixels or `50%` of the viewport image) drives the same ImGui events as the real mouse; in fixed-step runs the real mouse is ignored. `where [x y | on | off]` prints the camera's, its orbit target's and the cursor's coordinates (scene and game units; in a map context
also the map cell, and the cursor's height above the sea), `x y` probing the ground under that pixel; the same readout sits in the viewport's
bottom-left corner (View > Coordinates). With a tile open the game units are the launched battle's (`coords::BattleFrame`): centred on the
tile, height zero at the map's sea level at a map placement and at the variation's `min_height` (its number, as scene units) for the tile
alone, as the cameras of in-game captures fit (western_city_rome/small: the editor's (386.3, 9.8, 333.8) is the game's (-251.5, 44.5,
-356.5)). `luma` logs the auto exposure's black and white points, `cb <buffer> [variable]` a game constant buffer's values. View > Fog turns the distance fog off (the fog pass and the rivers' own fog), as `gfx fog off`.

`tile_studio.exe` (and its own renderer) was removed in Phase 8; the tile captures of `scripts/shots.sh` are the render regression.

Most edits of a tile publish only what they changed. Attributes (a name, a spline's values) refresh their items, a property the file lacks or a building's key makes its item again, a moved layer or group refreshes what is below it, the eye and the cursor add, remove or lock the difference (`tile_document/shift.rs`). Move to layer, group, ungroup, prefab updates, Resize, Restore walls and Generate SiegeAI publish the tile again. The minimap reads the siege overlays again only when something that feeds them changed (`Tile::siege_version`), and keeps each building's part.

**References (`ref_human`, `ref_unit`):** the Create panel's References category places real soldiers in the tile to measure the scale against, as many as
wanted: `ref_human` is one soldier, `ref_unit` a whole unit, its men from `main_units.num_men` at the game's unit size (`gfx_unit_size` in its preferences, read
again every few seconds), in the ranks and close spacing of its tables. They are tile elements like any other (moved, turned, grouped, undone; a click on any of a
unit's soldiers selects it), saved in `tile.wce` as `WceRefHuman` / `WceRefUnit` and dropped from anything TEd or the game reads. The Inspector picks the unit,
faction, animation slot, soldier and colours; an edit goes to every selected reference. They stand on the ground under each man, or level at their own height when
freeform. They aren't drawn in the Game view. Script: `tile_ref human|unit <x> <z> [unit] [faction] [soldier] [slot]`, `tile_ref status`.

**Tape measure (`WceMeasureLine`; TEd's Tape Measure, `TAPE_MEASURE_LINE`):** the Create panel's References category draws an open line of points on the ground
(clicks; Enter finishes, Esc cancels), as many as wanted. TEd's measure lines never reach a file it writes, and some versions lose them on save; ours are tile
elements like the polygons (points edited, moved, hidden, undone), saved in `tile.wce` and dropped from anything TEd or the game reads (Save for Assembly Kit lists
it as dropped; the game export is byte for byte the same with or without one). `wce_tile::measure` works out, for each stretch and the whole line, the length
along the ground (the terrain sampled every 0.5 m between the points), straight (3D), on the map (x and z) and the rise and grade (rise over the length on the map;
the whole line's from its first point to its last). The points stand on the ground, as a landscape polygon's do. The viewport labels every line shown with its length
along the ground (and straight, when it differs) at its last point, the selected one each stretch at its middle, and the line being drawn at the mouse; the
Inspector below the grid shows the totals and a table of the stretches. Commands: `tile_measure` logs the selected line's lengths, `assert_measure <ground>
<straight> <map> [tol]` tests them.

**Angle finder (`WceAngleFinder`; TEd's `ANGLE_FINDER_INSTANCE`):** next to the tape measure in References: three clicks on the ground (an arm's end, the corner,
the other arm's end; the third finishes it), kept and dropped as the tape measure is. It has three points always: inserting or removing one, or making one with
another number, is refused. `wce_tile::measure::angle` gives the angle at the corner seen from above (on the map) and in space (with the arms' rises), and each
arm from the corner out as the tape measure's stretches (along the ground, on the map, grade). The viewport draws an arc at each one's corner (a third of the
shorter arm, 1 .. 25 m) with the angle beside it, the one being drawn included; the Inspector shows both angles and the arms. Commands: `tile_angle`,
`assert_angle <on the map> <in space> [tol]`. TEd's other instance types and what the editor does with them: [formats/tile_ted.md](formats/tile_ted.md).

## Cross-tool composition (Phase 7)

Every open file is a `Document` in the one `DocumentManager`, whichever tool opened it. **Each tool has one document** (a tool's stand-in scene aside, the Weather tool's sample map): a tile and an `.environment` are open at once, each with its own history, modified marker and layer, but opening another tile closes the open one, another weather file the open weather file, and so on. With unsaved changes the replace prompt asks first: **Save and open**, **Discard changes and open**, **Cancel**; the old document goes only once the new one is open (if the open fails it stays, with its changes when they were discarded). Scripts: `open <path> [disk] [save|discard]` (it fails with unsaved changes and no answer, as `close` does; the tools' own open commands too: `close <doc> save|discard` first), `open_prompt <path>` opens the prompt as the menus would, `answer` answers it (`Editor::clear_to_replace`, `Editor::replace_document`). Opening a file of another tool switches to that tool (`open_path(..., switch_tool = false)` does not); a file that is open already is shown in its tool, not opened again. **The active document is the active tool's** (else its stand-in): the menus, History, `save`, `close` and the default Inspector target follow it, and switching tools switches document. Its title is at the right of the menu bar, `[Tool] title *` (amber while it has unsaved changes), and in the window's title.

| What | How |
|---|---|

## Saving and exporting

The user's work has one home, the game's **projects folder** (`Settings::projects_dir`; [plans/save_system.md](plans/save_system.md)).
**Save** always writes into it: tiles, maps and prefabs into `assembly_kit/` (the kit's layout), files opened from the game's packs (a
weather file, the weather database, a UI layout) into `loose/<their path in the packs>`. `loose/` is mounted before every pack, so a save is
what every tool reads from then on, the weather preview and Launch in game included: after each save the mounted files index the path
again (`Vfs::refresh_loose`, `Editor::loose_changed`, from `DocumentManager::take_saved`), no remount needed. **File > Revert to game's
version...** (`revert_to_game [doc]`) asks, deletes the project's copy (and the folders it leaves empty)
and opens the packs' file in its place. A file opened from disk saves in place. Each tool has its folder in the project (`Tool::project_folder`: the Tile tool
`assembly_kit/raw_data/terrain/tiles/battle`, the Prefab tool `.../art/prefabs`, the Terrain tool `.../terrain/battles`, the Weather tool
`loose/weather`, the UI tool `loose/ui`), made with `loose/` whenever the game's files are mounted (`Editor::make_project_folders`); File >
Open file starts in the active tool's, Save as in the document's own file's folder, a file of the packs' place in `loose/`, else its
tool's folder (`Editor::save_as_start`). Save as is off for a tile and a prefab stage (`Document::save_as_blocked`: a tile is its folder and its tile database entry, a copy elsewhere opens without its height range, size and colour; Tile > Save tile as and File > Export instead). A save marks a document saved only when it wrote the document's own file: a game file's copy outside its place in `loose/`, or a map's outside its projects folder, leaves it unsaved, as its own file lacks the edits.

Everything written for the game or for TEd is under **File > Export**, from the active tool (`Tool::export_menu`); each entry asks for its
destination and remembers the last one per game (`Editor::export_dir`, `pick_export_folder`, `pick_export_file`; `[games.<id>]
export_dirs`), and its script command takes the destination as an argument:

| Tool | Export entries |
|---|---|
| Tile | For Assembly Kit (`save_for_kit [raw_data]`, the kit prompt when several fit), As exported tile... (`save_exported [folder]`), To mod pack... (`save_to_pack <pack>`) |
| Prefab | For Assembly Kit (`prefab_save_kit`) |
| Terrain | Built files... (`terrain_export [folder] [--wait]`; also the Export section's button) |
| UI | Layout into a mod pack..., Project as a mod pack... (`ui_export <pack>`), XML... |

**Sharing projects** (File menu, after Export, from the active tool: `Tool::share_menu`; the Tile tool's in `share_prompt.rs`, the format in
`wce_tile::share`). *Share project...* (`share_project <zip>`) writes the open tile's project into one zip: every variation of its location
folder (no `.bak` or dot files), its database entry, and the projects' prefabs its references use, followed into those they use, with the road
pieces (`roads_proc/<type>`) of its roads' types; the tile has to be saved. Prefabs of the Assembly Kit are not copied: the manifest
(`wce_share.txt`) names them, and those found nowhere. *Import shared project...* (`import_shared <zip> [overwrite]`) puts it into
`<projects>/assembly_kit/raw_data` and opens its tile: new files are written, identical ones skipped; when a file differs, or the tile's
folder holds files the zip lacks, a prompt lists them and Overwrite moves each aside to `.bak` first (Cancel writes nothing). Another game's
zip, and paths that would land outside the projects folder, are refused; the tile open in the editor is not replaced under it. The import
names the kit prefabs it uses that this editor does not find.

Throw-away build files (the launch staging folders, dry runs, the export a terrain launch makes) go to `<projects>/build`
(`Editor::build_dir`), which nothing reads back between runs. Until the release, an interactive start offers once per game to move the old
output folder's edits of game files into `loose/` (`project_prompts.rs`: not the build files, `ui_xml/` exports or exports in the game's
layout; a file the project already has stays).

## Layouts

ImGui runs with docking and no ini file. Each tool has its own layout file `<config folder>/layouts/<tool id>.ini` (see the folders below). Switching tools saves the leaving tool's layout and loads the entering one's; without a file the tool's `default_layout`
(DockBuilder calls; the base class builds the standard one: inspector right, assets/log/history below, viewport in the centre) is built. `layout save`,
`layout reset`, File menu entries and saving on exit (not in batch runs) manage the files. A layout that was never loaded (a switch before the first
frame) is not saved over the tool's file.

When what the Inspector shows changes to something (the selection, or the active tool's part of it: `Tool::inspector_subject`, the Tile
tool's mode, brush settings, flip panel, what it places; the Weather tool's environment file) and the Inspector is a tab behind another in
its dock, its tab is selected (`Editor::raise_inspector`, `gui::select_dock_tab`): without taking the keyboard's focus, unless the focus is
in another tab of that same dock (a dock keeps its focused window's tab in front), where the Inspector is focused. Only on a change: a tab
picked over it stays in front while nothing it shows changes; a tool switch only takes the new tool's as the start.

A plain interactive start opens the tool the last interactive session was in (`last_tool` in the settings, kept on every switch,
`Editor::restore_last_tool`). `--tool <id>` starts in that tool instead and leaves `last_tool` alone, and so does any scripted run (`--script`,
`--cmd`, `--open`, `--tile`, `--shot`, `--capture`), so that scripts start where they expect.

| Tile: the projects in the kit's layout (tests) | `WCE_TILE_WORKSPACE` |

Until the first release, a missing `settings.toml` is filled from the old `key=value` `wce.ini` (in the same folder, or in `~/.local/share/awe` /
`%LOCALAPPDATA%\awe`) and its layouts are copied; the old folder is left alone (`settings/legacy.rs`, to be removed).

**File > Settings...** (command `settings open [page] | close | apply`, `settings_window.rs`) edits every setting on pages (General, Game,
Appearance, one per tool with settings, Folders) on a copy of the settings: OK and Apply put it in place, write the file and pass on what changed (the
frame cap at once; other mod packs or loose folders remount the packs; a new game folder is used from the next start; another game switches to it,
below); Cancel drops it. A field an
environment variable overrides says so. A tool adds its page with `Tool::has_settings` / `draw_settings` (on the copy, its own table) and hears of
applied settings in `settings_applied`.

### Games

The supported games are `wce_foundation::game::GameProfile`s (`ATTILA`, `ROME_2`, `THRONES_OF_BRITANNIA`; docs/plans/rome2.md,
docs/re/thrones_renderer.md): what the editor needs to know
of each (Steam folder, preferences file, rpfm schema, campaign battle map, default environment, where its packs come from, whether its
kit has the tiles). `game` in the settings names the current one (`Editor::game`). The toolbar's game combo (its first item) and the Settings window's Game page
switch it live (`Editor::switch_game`; command `game [key]`): the documents close (the unsaved-changes prompt asks first), each tool drops what was the old
game's (`Tool::game_changed`), and the game's packs and the renderer are made again; a game not set up yet opens the first-run dialog,
which has the same choice of game and **Back to <the game before>** (mounted again as it was) to back out. Each game keeps its own `[games.<id>]` table and projects folder.
The db tables (the buildings' data, the weather's climate phases, the procedural walls' rows) are read with rpfm's schema of the game
(`wce_foundation::settings::rpfm_schema_path`): `$WCE_RPFM_SCHEMA`, else the game's file (`GameProfile::rpfm_schema`) in the **DB
schemas** folder (Settings > General, `db_schemas`, `$WCE_DB_SCHEMAS`; every game's), else in rpfm's own schemas folder.
**Graphics** (Settings > Game, per game; docs/re/graphics_options.md): the game's own options (its `preferences.script.txt`, the
default), or the editor's copy (`[games.<id>.graphics]`: `use_game = false`, `options`), never written to the game's file; the game's
options as its options screen has them (`GameProfile::graphics`), its presets (the values its engine sets, the texture quality by
the card's video memory), each option marked when the renderer does not apply it yet. Editor only: the render scale (50 .. 100 %,
`render_scale`, `sharpness`): the scene drawn smaller and enlarged with NVIDIA Image Scaling.

### Appearance

`theme.rs`: the UI font is Inter with Lucide's icons merged in (`icons.rs` names them; the private use area is taken out of Inter, which has glyphs
of its own there), and Dear ImGui's vector font is the monospace one (the log). Themes: `dark` (the default: neutral greys, one blue accent, soft
corners), `light`, and `imgui` (Dear ImGui's own dark style); `[appearance] theme` and `font_size` pick them. The style is built again between frames
when the appearance changes, so the Settings window shows a change at once. Panels take the colours with a meaning (error, warning, modified,
success, highlight, the dim text) from `theme` instead of fixed values, so that every theme keeps them readable; what is drawn over the 3D view keeps
its own colours. Appearance > "Dear ImGui's style editor" edits the live style, to work on a theme.

### Shortcuts

`shortcuts.rs`: every key the editor and its tools react to is an action (id, scope, group, label, up to two default keys): the editor's
(`shortcuts::EDITOR`: save, undo / redo, the tools 1..9, the gizmo, focus, global / local, the camera's held keys) and each tool's
(`Tool::shortcuts`: the Tile tool's grab, box select, delete, duplicate, turn, group, copy / paste, quick add, rename, placing and grabbing keys;
the UI tool's delete, duplicate and nudges). Code reads `shortcuts::pressed(id)` / `down(id)` and menus show `shortcuts::label(id)`. A chord matches
when its key is pressed and Ctrl, Shift and Alt are exactly its own; a held action ignores Shift unless its chord has it, and a modifier key bound
alone (the camera's *faster*, Left / Right Shift) matches whatever else is held. A key may be a mouse button too, the middle, Back or Forward one (`MouseMiddle`, `MouseX1`, `MouseX2`; not the left and right buttons, which pick and turn the camera): it counts when clicked, released within 4 pixels of where it went down (a middle drag still pans), and a viewport's action reads it over the viewport only (`shortcuts::pressed_here`). Variants are actions of their own (*Turn back*, *Paste in place*).
Dialog keys (Esc cancels, Enter confirms) and text editing are not actions. **Settings > Shortcuts** lists them by group with a filter: a click on
a key reads the next key pressed with its modifiers (no action fires meanwhile; a click again stops), the cross clears it, the arrow puts the defaults
back, *Reset all*. Two actions whose keys are read at the same time (the same scope; the editor's with any; the viewport's with a tool's) may not
share a key: such keys are red, the tooltip names the other action, and OK / Apply wait until it is changed. `[shortcuts]` in settings.toml keeps
only the changed actions (`undo = ["Ctrl+K", ""]`). Commands `shortcut <id> [key 1 | -] [key 2 | -]`, test `assert_shortcut_clashes <n>`.

When the game folder is not set or does not exist the editor starts without the game and shows the first-run dialog: it picks the game, fills in the Steam
library's folder of it (registry `SteamPath` + `libraryfolders.vdf`), lets you browse, and **Save and continue** (command `setup`) writes the settings, mounts
and starts the active tool; **Quit** leaves the editor. Its mod pack list (also File > Mod packs and the Settings window's Game page) has a search
field, and drops the chosen packs that are no longer in the game's data folder (named above the list; saving the settings removes them).

`frame_cap` (View > Frame rate cap, command `frame_cap`, environment `WCE_FRAME_CAP`; default 60, 0 = none) holds an interactive session to that many frames per
second: rendering the scene as fast as a fast laptop display refreshes kept the GPU at 100 % until it throttled itself (to 180 MHz of 3090 on the RTX 5070 Ti
laptop, 10x slower frames). Shots, captures and frames while a script runs are not capped (perf measurements stay the real cost of a frame).

## Command line

```
wce.exe [--tool <id>] [--open <path> | --open-disk <file>] [--cam yaw pitch dist [target_y]] [--cmd "<command>"]... [--script <file>]
        [--frames N] [--shot <file.png>] [--capture WxH <file.png>] [--fixed-step <seconds>] [--live] [--background | --foreground]
```

`--shot`, `--capture` and `--script` runs are unattended: their window is created non-activating, kept out of the taskbar and Alt-Tab and put behind the other windows, so a test run never takes the focus from a game or an editor in use. `--foreground` (or `WCE_FOREGROUND=1`) brings back
the normal window, `--background` (`WCE_FOREGROUND=0`) makes an interactive run quiet too.

Everything becomes a script: `--tool` and `--open` first, then `--cmd` / `--script` in order, then `frames N` + `shot` (the whole window after N rendered frames) or
`capture` (the scene offscreen, no window involved), then `quit`. Shots, captures and scripts run on the fixed-step clock (1/60 s per rendered frame), so the same
script gives the same pixels. Exit code 1 when a script line fails.

Script format: one command per line, `#` comments, double quotes group, a leading `-` lets a line fail, `frames N` waits N rendered frames. `help` in the Commands panel (or as a command)
lists them all. Test commands (`assert_*`) fail the script when they do not hold; `key Ctrl+2`, `click_item 13`, `move 3 5 0 2` drive the same code paths as the keyboard,
mouse and gizmo.

## Gizmo and ImGuizmo

ImGuizmo wants row-vector matrices (v * M, row-major); the engine's are column-vector (M * v), so the viewport passes transposes (`to_gizmo` / `from_gizmo` in `viewport.cpp`). The gizmo moves the
first selected item's pivot (`Document::item_transform`); the change since the last frame, `new * inverse(old)`, goes to `Document::transform_items` for every selected item with a gesture id,
so a whole drag is one undo entry. Scale is accepted by the gizmo but a document may ignore it (the sample map does).

## Selection outline

The selection is drawn as an outline around its silhouette (`Renderer::pass_selection_outline`, an editor pass like picking, not a game
shader): the selected meshes and terrain (through the draw sets, as the id pass draws them) and the selected overlays go into a mask at the
viewport's size, once whole and once against the scene's depth; a full-screen pass colours the pixels within `selection_outline_px` of the mask,
solid next to the visible parts and faint (35 %) next to the hidden ones. Colour and width come from the editor (`Editor::selection_outline_style`:
the theme's highlight, 2 px times the display's scale; 2 px in scripted runs). An item without a mesh of its own is outlined from an overlay
that is drawn only into the mask (`Overlay::selection_mask`): the Tile document puts the selected markers' shapes there (`set_highlight`),
and keeps only a selected polygon's point handles in its visible highlight. A selected light keeps its reach box. With 672 wall pieces of the
Ravenna tile selected a frame takes about 0.3 ms more (it took 7.6 ms more when the selection's entities were looked up item by item).

## GPU

`libs/render/gpu_adapter` chooses the D3D11 adapter: `WCE_GPU=<part of the adapter name>`, otherwise the high-performance GPU, and the renderer logs `GPU: <name>` when it starts. Two GPUs do not round float math the same way,
so reference pixels only compare on one adapter (the gate scripts default `WCE_GPU` to `AMD Radeon`, see `docs/baseline.md`).

`WCE_D3D_NO_DRIVER_THREADS=1` creates the device without the driver's internal threads (slower): the access violations in `amdxx64.dll` happen on the driver's worker thread, after the call that caused them, and with this one happens in that call, with the editor's stack in the dump. `WCE_D3D_DEBUG=1` is the debug layer, whose messages only reach a debugger.

A colour target and a depth view must have the same sample count: with MSAA the particles' distortion buffer (one sample) takes the read-only one-sample depth, not the scene's. Paired with the scene's, the runtime let it through and `amdxx64.dll` crashed on its worker thread some time later; only the debug layer turns such a pair down. Its messages go to the debugger, not to the log: run `WCE_D3D_DEBUG=1` under `cdb` and search the output for `D3D11 ERROR`.
