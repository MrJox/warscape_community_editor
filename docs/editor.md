# The editor shell (`libs/editor`, `app/`)

`wce.exe` is one window with one renderer and one shared scene; tools are modes of it. Phase 4 built the shell, Phase 5 moved the Weather tool onto it
(`tools/weather`, see below), Phase 6 the Tile tool, Phase 7 lets the tools share documents (see Cross-tool composition).

## Pieces

| Piece | File | What it does |
|---|---|---|
| `Command`, `CommandStack` | `editor/command.h` | undo/redo per document; a drag gesture pushes many commands with one merge key and ends as one entry (`break_merge` when the gesture ends); `modified()` follows the saved position |
| `Document` | `editor/document.h` | one thing a tool edits, with its lossless model inside: `publish` into its scene layer, `outline`, `inspect`, `item_transform` / `transform_items` for the gizmo, `save` |
| `DocumentManager` | `editor/document_manager.h` | owns the open documents, one `RenderScene` layer each, re-publishes a document when its stack moved; `unsaved`, `save_one`, `save_all`, layer visibility, the stand-in scene rule |
| `Selection` | `editor/selection.h` | a set of `SourceRef` (document, item); the scene entities that show them come from `RenderScene::entities_of` |
| `Inspector` | `editor/inspector.h` | the documents describe an item through this interface; every property has a `PropertyPath` (document, item, field), the seam the Cinematic editor animates through; `panels.cpp` has the ImGui implementation |
| opening what is open | `editor/editor.rs` (`open_path_with`) | a document is not opened twice: a pack file whose `source_key` is open, or a disk path a document says it came from (`Document::opened_from`: a tile's folder, any file in it, its entry, or the kit's folder whose project it is) activates the open document |
| `CommandRegistry`, `ScriptRunner` | `editor/command_registry.h` | every action is a named command; menus, `--cmd`, `--script` and tests all run the same entries |
| `TotalWarCamera`, `TopDownCamera`, `WalkCamera`, `FlyCamera`, `OrbitCamera` | `wce_editor_core::camera_controller` | viewport cameras on the game's battle lens (FOV 65 degrees, near 1, far 13000); the top-down view is orthographic. The ground and the models' bounding boxes they keep out of: `wce_editor::camera_world` |
| `Viewport` | `editor/editor.h`, `viewport.cpp` | renders the scene into a `RenderTarget`, camera input, click to select (through `Renderer::pick`), the ImGuizmo gizmo (translate/rotate/scale, snap), offscreen `capture` |
| panels | `editor/panels.cpp` | Inspector, Assets (the VFS tree, filter, only the tool's file types, double-click opens), Log, History (click to jump), Commands (console) |
| `Editor` | `editor/editor.h` | the host window with menu bar, tool switcher and dockspace; owns VFS, renderer, scene, documents, selection, clock; layouts; first run |
| `Tool` | `editor/tool.h` | a mode: opens, panels, menus, viewport input, default layout, commands; `PlaceholderTool` for the future ones |

`libs/editor` is two targets: `wce_editor_core` has no ImGui or GPU code and is what `cli/editor_check` tests; `wce_editor` is the UI.

## Tools

Registered by `app/main.cpp` through `tools/tool_factories.h`: Weather (Phase 5), Tile, Unit, VFX, Terrain (placeholders with a
panel that says what is planned). Now `wce_app::tools`, one Cargo feature per tool: Weather, Prefab, Tile, Terrain, UI, Audio, Unit, VFX,
Cinematic (below). **Ctrl+1..9** switch tools.

To add a tool: derive from `Tool`, give it an id and title, return the file extensions it opens, implement `open` (return a `Document`), add panels in
`draw_panels`, commands in `register_commands`; add a factory to `tool_factories.h` and register it in `main.cpp`.

## Weather tool (`tools/weather`)

Opens `.environment`, `.lighting` and `.xml` (weather definitions; `vfx/` files are the [VFX tool](#vfx-tool-wce_vfx_tool)'s and are refused here) from the packs or from disk (File > Open file, `--open`, `--open-disk`, double-click in Files). Each file is an
`XmlFileDocument` around the lossless `XmlDoc`: attribute edits are `XmlAttrCommand`s (merge per drag gesture), structural edits (duplicate, delete, move, add child or attribute,
remove attribute) are snapshot commands. Save writes a file of the packs as a loose file into the project's loose folder (`<projects>/loose/<its path in the packs>`, `Editor::loose_path`; the game's `data` folder is never touched; see [Saving and exporting](#saving-and-exporting)), re-reads it as
the new baseline and clears the history, so the saved bytes differ from the pack file in the edited spans only.

The **Inspector** of an `.environment` / `.lighting` file groups its settings by effect (Sun, Ambient light, Sky, Fog, Exposure and tone mapping, Colour grading, Depth of field, Water, Wind and snow, Precipitation node, one Cloud layer per plane, then Other attributes), each with a tooltip (`wce_weather::environment_sections`, `Tool::inspect` of the weather tool; the Properties tab keeps the raw XML tree for everything else). A setting the file lacks shows dim at the value the viewport assumes (`EnvironmentParams::default`) and is added to its element (`Op::AddAttr`) when edited; a number the file writes as an integer stays one while it is whole. Attributes of these elements that no section lists, like the single `low_tones_bias` the battle game ignores, are under Other attributes. A missing element (a `.lighting` has no `SKYGEN`) is not added.

| Old weather_editor feature (`docs/plans/weather_current_state.md`) | Where it is now |
|---|---|
| Files browser with filter and categories | **Files** panel (and the shared Assets panel, filtered to the tool's types) |
| Properties tree with typed editors, search, per-attribute revert, add / remove | **Properties** panel (tree) and the shared **Inspector** (typed editors for bool, int, float, colour, variance, euler, string) |
| Structural edits with snapshot undo | context menu in Properties; `xml_op`; Ctrl+Z / Ctrl+Y, History panel |
| Changes tab | **Changes** tab of Properties (every modified attribute of the file, revert) |
| Live preview on the sample map, orbit camera, battle lens | shared viewport; the tool's environment document lights `RenderScene::environment` every frame (while the tool has `weather_definitions.xml` open instead, the last environment it had, as saved; a default dry environment when none) |
| View modes (HDR, albedo, normal, depth, ...) | **Weather scene** bar and `view <n>` |
| Sample map seed and count, re-roll | **Weather scene** bar, `sample`, `reroll` |
| Graphics options (gamma, brightness, SSAO, DOF, shadows, vignette, flare) | **Settings** menu (read from `preferences.script.txt`) |
| Weather selection database: Pick and Edit tabs (flag bits, categories and values with the game's locked unless Expert, clone a map / climate, coverage grid, conditions grid, problems for the game, undo), Open / Save / Save As / Convert `.xml` and `.bin` (docs/re/variation_db.md). A game without the database (`GameFeatures::variation_db`; Rome 2 picks by the weather folders) has the item disabled, with why | **Selection > Weather picker** (`WeatherPicker`, `VariationEditor`), `picker`, `pick k=v`, `vdb-script` |
| CLI `--open`, `--open-disk`, `--cam`, `--frames`, `--shot`, `--capture`, `--view`, `--blend`, `--pick`, `--picker`, `--vdb-script`, `--no-flare` | same flags of `wce.exe`; the weather ones are commands of the tool (`--name args` runs the command `name`) |

**Visual editing** (`visual.rs`, an `.environment` / `.lighting` file open): the **sun** is a disc in the sky of the viewport where the game draws it; dragging it puts the sun under the cursor, and **Ctrl+L** held over the viewport turns it with the mouse's motion (sideways the azimuth, up and down the elevation, 0 to 90; Unreal's shortcut). The angles are the file's (a tile's battle frame turn taken off), to a tenth of a degree, and one drag is one undo entry (`XmlFileDocument::edit_setting`, `join_last`). The **Weather scene** panel has *Compare with saved* (also **C** held over the viewport, `weather_compare on|off`: the file as saved, the project's loose copy or the packs', lights the scene instead of the edits, with a banner; exposure adapts across the flip as in the game), *Pick focus* (`weather_pick_focus`: the next click sets DOF_focus to the view depth of the surface under it; ASSUMPTION: the shaders compare it with view depth) and *Tone curve and histogram* (`weather_tone_panel on|off`: the per-channel S-curve of low_tones_bias / high_tones_bias as the engine bakes it, the frame's brightness histogram with the clipped and crushed share, read back twice a second only while open, and the adapted black and white points). The **wind** is an arrow on the ground at the camera's target, the way it blows (grey while wind_dir_random lets each battle pick); dragging its head sets wind_dir_degrees to a degree (the scene's turn taken off, as `Renderer::wind_direction_degrees` adds it). *Mix with another file* (`mix.rs`, `weather_mix <file> <t> | off`, `weather_mix_save <path>`): while the section is open the viewport cross-fades the open file to another (`blend_environments`, the game's cross-fade), and *Save the mix* writes it as a new `.environment` of the project's loose folder: the nearer file's text (its switches, texts and cloud layers) with every number of the sections the mix's (`XmlFileDocument::write_numbers_of`); a name the packs or the project have already is refused, and the new file is opened when the open one has no unsaved edits. The sun and wind handles are off while comparing or mixing. *Fog distances* (`weather_fog_rings [on|off]`; no argument logs them) rings the ground around the point below the camera where the fog over it reaches 25, 50 and 75 %, from the fog shader's formula ([re/renderer.md](re/renderer.md), "Battle fog"): the distance fog, the height fog at the ground's height and the clear distance's fade-in; they follow the camera as the fog does, and show the game's fog (the camera chip's fog amount thins the drawn fog, not the rings). The sun handle: Ctrl+L held owns the sun (a click meanwhile is swallowed), and a drag of the disc keeps it until its release. `weather_sun_disc` and `weather_wind_tip` say where the handles are, for scripted drags. *Compare with saved* splits the viewport: the file as saved left of a line you drag, drawn by a **preview renderer** (`preview.rs`, `Renderer::new_sharing`: the main renderer's models and textures, its own exposure, cubes, wind and particles, so neither disturbs the other; shown without a copy, `ImageTextures::show_view`, under the compass, `Tool::viewport_underlay`; dropped after 10 s idle); holding C flips the whole view. *Preview without* (`weather_without <part> on|off`) takes fog, clouds, precipitation, the tone curve, colour grading or depth of field out of the viewport's light only, with a banner. The Inspector's **Fog** section ends with the fog's opacity over flat ground by distance (`Inspector::plot`), its **Sky** section with two **sky strips**, the game's sky looking up towards the sun and away from it through the whole pipeline (`sky_strip.rs`, `Inspector::images`, `inspect_environment_with`; `weather_sky_png`): each by a preview renderer of its own, drawn again once the light has been still for 0.3 s (not during a drag: each drawing makes the preview's cubes again) and shown from its target without a copy back. The Inspector's sections fold (`Inspector::open_section`, open by default). The histogram's copy of the frame comes back without waiting for the GPU (`image_io::Readback`). The **Weather gallery** (Files > Gallery, `weather_gallery on|off|refresh [filter]`, `gallery.rs`) draws the listed .environment files (60 at most) on the scene from the camera of when it opened, one per frame; a click opens one. A **reference screenshot** (`reference.rs`, `weather_reference <png> [over|corner|off] [opacity]`): a PNG fitted to the viewport keeping its proportions, over it at an opacity or in its corner; *Compare a spot* (`weather_reference_compare x y`) gives the screenshot's colour and the render's at a click, and how they differ in brightness and warmth (a guide: the files' colours are lit and tone-mapped, so a picked colour is not written into the file; the two must be framed alike). The keys are in Settings > Shortcuts (Weather). The ideas not done yet: [plans/weather.md](plans/weather.md), Open 3.

Differences: the legacy app held one active file; here every open file is a document, and the one that lights the scene is the last active `.environment` / `.lighting`. `weather_editor.exe` was removed in Phase 8; the render regression is the `wce.exe` captures (`scripts/shots.sh`). `scripts/weather_check.sh` supersedes `variation_e2e.ps1`.

## VFX tool (`wce_vfx_tool`)

Behind the `vfx` feature of `wce_app` (off by default: `cargo run -p wce_app --features vfx`); the plan and its decisions are
[plans/vfx_tool.md](plans/vfx_tool.md). It opens `vfx/*.xml` (`Tool::opens_under`: a file under `vfx/` comes here whichever tool is active)
as an `XmlFileDocument`, so saving, autosave, undo and the byte-identical round trip are the Weather tool's: Save writes the project's loose
copy, different from the pack's file in the edited spans only.

- **Files**: the effects of the packs (and the project's loose copies), filtered; mod files in blue; double-click opens. *New...*
  writes a new effect into the project and opens it (`new.rs`): a copy of the open one (its edits included), or one that plays a library
  effect as the game's own do (an empty `<vfx>` and one reference enabling every emitter of the library, in the game's text layout:
  UTF-16 with a BOM, CRLF, tabs). A name the packs or the project have is refused.
- **Viewport**: the effect plays where the *spot* is (a `Payload::VfxEmitter` entity in the document's layer, the path tile VFXInstances
  use), on the sample map or the open tile, lit by the editor's weather preview (else the Weather tool's open environment, taken when
  the tool activates; else the default day). The spot is dropped on the ground where the
  camera looks; *Here* moves it there again, the move gizmo drags it. The tool's own edits play live: the editor's **particle overlay**
  (`wce_editor::particle_overlay`) feeds every open vfx / weather definitions document to the particle reader, whichever tool is active,
  and the placed effects that read a changed file (their own or a library they play) read their definitions again, in place, the
  others not (`RenderSettings::vfx_changed`, `ParticleSystem::reload_world_files`).
- **VFX preview** panel: Play / Pause (**Space**), Restart (**R**), speed (`RenderSettings::particle_time_scale`: the particles' clock,
  the weather's included), loop every N seconds, the spot, handles on or off, what the move gizmo moves (the spot, or the focused part's
  `SpawnPosition` / the focused reference's `pos_*`, an edit of the file), and the **Parts**: each emitter and reference with Solo,
  Mute and Focus. Solo and mute are preview-only bytes laid over the file in the overlay (`Editor::set_particle_override`), never
  saved.
- **Inspector** (the shared framework): *Effect* (the `<vfx>` attributes, the quality variant edited, a property filter, only the
  focused part), then a section per emitter (its properties grouped Emission, Particles, Spawn shape, Motion, Culling, Rigid models,
  Other; readable labels, what each does and its XML name in the tooltip; a property the chosen variant lacks shows the base one dim),
  per behaviour chain (each modifier's properties; `vs_colour` with its colour ramp, `vs_vertex_alpha` with its opacity over life),
  the render stacks, and per reference (position, scale, start time, and per library emitter enable, tint range, lifetime biases;
  *Open the library*). Curves (`SpawnAreaCurve`, `SpawnAreaBox`, `EmissionRateCurve`...) are **curve editors**
  (`Inspector::edit_curve`): drag a key, double-click to add one, right-click to remove one; the drag plays live and is written as one
  undo entry when it ends, rewriting only that property's text (`XmlDoc::with_inner_text`). A drag over several attributes (a colour's
  channels, min and max) is one undo entry (`XmlFileDocument::set_attrs`). Numbers keep the file's style (`0.00` stays two decimals
  unless the value needs more). Duplicate an emitter (with a render stack of its own, so the copy draws), a chain or a reference;
  delete an emitter (with its place in the stacks), an unused chain or a reference: one undo entry each. *Add a property* (per emitter
  and modifier) lists the properties the game's own emitters of its type (or modifiers of its fragment) have and this one lacks, and
  adds one as they most often write it (`defaults.rs`: the engine's defaults are not decoded, so vanilla's files, read once on a thread
  of their own, are the defaults); with a lower quality variant edited, it also adds that variant of a property the emitter has only in
  the base (a copy of the base line). Editing a dim row (the base shown for a variant) edits the base.
- **Handles** of the focused part: the emitter's spawn ring (inner and outer radius, its arc) and box drawn where particles are born,
  turned by `EmitterRotation` and moved by `SpawnPosition`, its spawn directions (the `SpawnSpread` cone, or straight out); their dots
  drag the ring's radius and the box's x, z and y size (the curves scaled; Ctrl to tenths; a shape of size 0 has a hollow dot to drag
  out). A dot under the mouse hides the move gizmo, whose arrows it may sit on.
  References show where they play and their scale.
- **Commands**: `vfx_play [on|off]`, `vfx_speed`, `vfx_restart`, `vfx_mute`, `vfx_solo`, `vfx_focus`, `vfx_only_focused`, `vfx_filter`,
  `vfx_quality`, `vfx_set <emitter> <property> <attribute> <value>`, `vfx_curve <emitter> <property> <curve> <t,v;...>`,
  `vfx_duplicate`, `vfx_delete`, `vfx_new <name> copy | plays <library>`, `vfx_add_property <emitter> [property [quality]]`,
  `vfx_handles` (the handles' pixels and values), `vfx_drag_handle <handle> <dx> <dy>` (a mouse drag from where it is), `vfx_frame`,
  `vfx_info` (the parts, their curves, what plays, the particles and their errors).

## Tile tool (`tools/tile`)

A tile's root is its tile database entry (`_tile_database/TILES/*.xml`, [formats/tile_database.md](formats/tile_database.md)): it names the folder of `tile.ted` (location + variation) and holds the size, colour, ground groups, height / normal parameters and links. Open one with the **Tiles** panel (the kits' entries from an index, no scan; word filter; double-click opens the first variation, a button per variation; above the list, **Favourites** (the star at a row's right, `tile_favourite <key>`) and **Recently opened** (the last 10 tiles opened, with the variation, which a double-click opens again), both of the panel's source and under the same kind and word filters, kept in `[tools.tile] favourites` / `recent` (`tile_marks` logs them); an exported tile opened into a workspace counts as the packs'), Tile > Open tile... (an entry `.xml`, a `tile.ted`), `--tile <target>` or the `tile <target> [variation]` command, where the target is an entry file, a name (`assembly_kit/osgiliath_test`, or the entry's file name), a variation folder, a tile folder (opens its first variation) or a `tile.ted`. A folder or `tile.ted` resolves its entry from the path; outside a kit there is none and the tile opens with a warning and no height scale. The **Tile** panel shows the entry read-only (colour, size, flags, ground groups, a variation chooser that opens the other variation in this one's place, the variations' height / normal / overlap values, links and targets). A `TileDocument` wraps a `TileProject` (the lossless `TedScene` and the `HeightField`), and everything it does is a `Command` on the document's stack:
attribute edits on the scene (moves, rotations, polygon points) merge per gesture, structural edits (duplicate, delete, add building, polygons, layers) keep whole-document snapshots, and a brush stroke is one entry however many steps it took. Items are element indices + 1 (item 0 is the terrain), so the shared
selection, inspector, gizmo and history work on them.

**Problems** (`wce_tile::vegetation::trees_outside_exclusions`): BOB keeps a manual `VEGETATION_INSTANCE` only when it stands inside a `VegetationExclusionPolygonInstance` (none when the tile has no such polygon), so the others never reach the game. They are listed in the Tile panel's *Problems* (a click selects and frames one; `tile_problems` logs them), an error in the log when the tile opens, and a warning at the front of every save's message.

**Where tiles are saved** (`wce_tile::project_files`, `tile_document/kit.rs`; the files: [formats/tile_wce.md](formats/tile_wce.md)): a tile is saved as **`tile.wce`** in the game's projects folder (`<projects>/assembly_kit`, laid out like a kit's `raw_data`: the tile at `raw_data/terrain/tiles/...` and its entry in `_tile_database/TILES`), never in the Assembly Kit. A tile's variations can be one project instead (**Tile variations** below): `tile.wce` in the tile's folder, no variation folder of its own. `tile.wce` is a superset of `tile.ted`: the same XML, the root `<project>` marked `wce_version="1"`, where the editor may keep what TEd does not know, named so that the conversion finds it: an attribute `wce_...`, an element `Wce...`. Numbers are kept at full precision (`format_number`: positions, orientations, points, handles, areas); TEd's precision is applied only by the conversion (`ted_number_text`: `%.6f` of the float32 trimmed, `%g` for points, handles and `lf_offset`, integers as they are, only where that is shorter, so what TEd wrote stays byte for byte: 2 of the kit's 39.9 million values would differ, `examples/ted_numbers_check.rs`). A placed prefab is a **reference**: an instance group with `wce_prefab="<key>"`, kept in tile.wce without its contents; the editor fills them in from the prefab when it opens the tile (`expand_prefabs`, prefabs placed in prefabs too) and leaves them out when it saves (`strip_prefab_contents`), so an edit of the prefab reaches every tile that places it. The conversion for TEd (and for the game export, which compiles the editor's scene) writes the group with its contents: TEd's copy. The first save of a tile opened from the kit makes its project (the tile's folder and its entry copied, `tile.wce` written) and the document goes on from there; opening a kit's tile that has a project opens the project. A project's entry lists every variation, but a variation is in the project only once it was saved: one that is not opens from the kit's copy (an extracted tile's is extracted from the packs, the entry keeping the other variations' numbers), and its first save brings it in, leaving the project's entry as it is (a save changes only its own variation's `min_height` / `scale` in the entry file). Save writes only what changed (the edited spans, the kit-exact PNG encoder for the height map, the river files of rivers that changed); `save_to <folder>` writes the tile elsewhere. **File > Export > For Assembly Kit** (`save_for_kit [raw_data]`) writes a tile TEd reads into the kit that has the tile's kind: `tile.ted` (`project_files::to_ted`: the polyfills of the editor's features, then what TEd lacks dropped, all in the log), every river file, the height map, the other files and the entry; files with other bytes keep a `.bak`, identical ones are left alone. **Tile > Import from Assembly Kit** (`import_from_kit`) opens the kit's copy of the project, whose next save replaces the project. A tile **extracted** from the packs (`open_exported`) is decompiled into the projects at its own folder, the kit's tile of that name and it sharing the project, and its `tile.wce` is marked `wce_extracted_tile="true"` (`project_files::EXTRACTED_ATTR`, dropped silently for TEd and the game; the Tiles panel shows a package on its row). Extracting a tile whose variation folder has a project already asks first (`extract_prompt.rs`): **Open the project**, **Overwrite** (the variation folder replaced; the entry keeps the other variations' numbers) or **Cancel**; `open_exported <folder>` opens the project, `--fresh` extracts over it. **Import from Assembly Kit** on an extracted tile extracts it again from the game. Projects of older versions kept extracted tiles at `<tile>_extracted` folders and locations: **Tile > Migrate old extracted projects** (`migrate_extracted`) moves them to their own names and marks them, leaving any whose place has a project, or that is open, as it is (listed in the log).

**Several Assembly Kits** (Settings > Game, `GameSettings::assembly_kits`; `WCE_ASSEMBLY_KIT` is a `;` list): one list is the single place that says where the kits are, `Settings::assembly_kit_dirs` / `assembly_kit_raw_dirs` (a development install's battle tile map kit brings the campaign one; with no list the kit in the game folder is used). The Tiles panel lists each kit's tiles (a kit whose folder name another shares is named by its whole path), the prefab library reads every kit's `art/prefabs`, and where a tile or prefab is in several kits the first of the list wins (Import from Assembly Kit, opening a variation the project does not have yet). "Save for Assembly Kit" asks which kit when several fit (`kit_prompt.rs`; the `save_for_kit` and `prefab_save_kit` commands take the first, or a raw_data folder). The old single `assembly_kit` setting is moved into the list when the file loads.

**Launch in game** (the `wce_launch` crate, shared with the Terrain tool; `launch_prompt.rs`; [plans/launch_in_game.md](plans/launch_in_game.md), the command line in [re/game_command_line.md](re/game_command_line.md)): **Tile > Launch in game** (`tile_launch_game [--dry-run] [--ignore-movie-packs] [--async]`) exports the open battle tile, writes a battle XML (`script/wce/wce_launch.xml`) and starts the game with `show_frontend_movies false; game_startup_mode battle script/wce/wce_launch.xml;`: the game goes straight into a battle on the tile; `used_mods.txt` is not touched. The work runs on a thread behind a progress window: the steps (the game's tile data the first time, the compile, the packs the tile needs, the launch's files, the start), what the step going on is doing (`wce_foundation::activity`: each compile stage, each climate's trees and props, the grass, the dependency scans, with their times), the time taken and the time left from the last launch's steps (`[tools.tile] launch.step_seconds`), Cancel. **Delivery** (Settings > Tile, *Launch in game*): *launch pack* (default, below) or *loose files*, written under the launch's folder (`<projects>/build/launch/<id>/game`, `Editor::build_dir`) and given as `add_working_directory`, with only the mod packs chosen in the editor that the tile needs (`launch::needs`: the buildings' `rigidmodels/buildings/<key>/` files, every asset path in the shipped files and in turn in the models and definitions they name, the climate's ground textures and grass, the weather file, the pack each is read from; the mod packs whose `models_building`, `main_units`, `land_units` or `factions` tables hold a key the release's tables lack); the game's packs win over loose files (the release's too: `tiles.pack` has the tile database), so a pack that loads with a path the tile ships, a tile with procedural walls (their database rows) or no mounted files make that launch use the pack, with the reason in the log: in practice every tile. *Launch pack*: `data\wce_launch.pack` (a mod pack with a marker) named first, then every mod pack chosen in the editor. Files the tile uses from the editor's loose folders (an edited weather file) go along either way. The battle: the tile alone as the map (its variation folder; `land_normal`, the playable area and deployment scaled from the tile's size; a tile with deployment zones gives each army the zone of its `deployment_area_alliance_index`, the defender's inside the walls, the attacker's ring, and puts its unit in it, `launch::Zone`), or the Map context's placement in the game's campaign map (`tile_map_position` = the placement's centre cell / the map's size, y from the top; `settlement_standard` and the *Tile upgrades* for a settlement tile set; the kit's maps are not in the game's packs, so they fall back to the tile alone);. The tile alone (also when a placement can't be used) is in the editor's climate (`launch_climate.rs`; `tile_launch_game --map tile|context`): the game draws a tile alone in the `default` climate (summer), so the launch pack gives `default` the look of the climate and season the editor draws the ground with: the tile's texture groups' ground textures (the season's, else summer, else `default`'s) under `default`'s summer names, the climate's models of the grass list's keys under `default`'s names (a key it has no model for, `default`'s rock and mud patches, leaves the grass list), and the climate's tree list and procedural props as `default`'s; the climate's texture scales and light parameters are still `default`'s; the editor's climate `default` is the game's own look of a tile alone; the tile's weather; one unit a side, the current game's (`[games.<id>.tools.tile] launch_army`; an empty key is the game's vanilla one, `GameProfile::launch`), and the elements its engine lacks left out (Rome 2: the alliances' indices, the tile upgrades). The game's executable, data folder, pack format and campaign map are its profile's; a launch being prepared or a launched game keeps its own game when the editor switches to another. **Linux** (`wce_launch::proton`): a game folder with the game's executable is the Windows build, started through Proton as Steam starts it: the compatibility tool Steam runs the game with (`config/config.vdf`'s `CompatToolMapping`, the game's app id, else the default; a custom tool of `compatibilitytools.d`, or Valve's folder in `steamapps/common` whose name reads as it), or the Proton folder of Settings > Tile (*Proton*); inside the Steam Linux Runtime its `toolmanifest.vdf` requires (each tool's `commandline`, verb `waitforexitandrun`), in the game's prefix `steamapps/compatdata/<app id>` (made by Steam at the game's first start). Wine quotes and escapes every `"` of a program's arguments, so the command line goes into `wce_launch.bat` in the launch's folder, run by the prefix's `cmd`; a loose launch's working directory is `Z:` + its path. The game does not inherit the editor's own DXVK-native settings (`proton::EDITOR_ONLY_ENV`: `DXVK_WSI_DRIVER`, `DXVK_LOG_PATH`): Proton's DXVK reads them too, and with `DXVK_WSI_DRIVER=SDL3` Attila crashed while a battle loaded (`Empire.Retail.dll+0x178c1b6`). A folder without the executable is a native Linux build, which is not launched. The process checks read `/proc` (Steam is its `steam` client). Before the start: the game must not be running, Steam must be, and a movie-type pack in `data\` that is neither the game's nor `@wce_proc_data.pack` opens a question (*Launch anyway*). The tool waits for the game (its `update`) and removes the launch's folder and pack when it exits; the other launches' folders go only when no game runs (a dry run clears only dry runs' `d...` folders); what an editor closed meanwhile left is removed at its next start. `--dry-run` does everything but the game; `--async` runs as the menu does.

**Texture rules** (`wce_tile::texture_rules`, `tile_document/texture_rules.rs`, `texture_rules_panel.rs` in the Inspector: the Tile panel's

base blend map is): what the tile's own painting holds in other textures stays (a kit tile's artist's work). They make one blend layer owned by them that lies **under** the user's
layers (hand paint goes over it; painting with no working layer goes into a `Painted` layer), made again off the editor's thread when
the terrain, the scene or the rules change. The tile keeps its rules in `texture_rules.wce` beside `tile.wce`; presets are files in the
projects' `raw_data/art/texture_rule_sets` (the built-in `Default`: mud by the water and in hollows, worn ground by roads and buildings,

The ground coverage (`ground_coverage_panel.rs`) stays a window of the Tile panel's Experimental section; its kinds are Inland cliffs, Coast, Riverbanks, Shores (the walkable banks and their shallows: reeds and stones, built-in sets when none is chosen) and Around buildings (`ground_coverage <preview|generate> <kind> <preset> [seed] | window | close`). They (`styled.rs`) show

**Advanced** (every number), in a label column and a value column that keep their places; a condition is a check box and a bar that draws

picked from the tile's groups' and variations' swatches. Keys a biome grows or a clutter rule lays (when not a set) are picked from the game's own (`key_picker.rs`):
shown as their thumbnails (a key the game's files lack framed red), a click takes one out, the + cell opens a searchable grid of the

**Erosion** (`wce_tile::erosion`, `tile_document/erosion.rs`, `erosion_panel.rs` in the Inspector: the Tile panel's Terrain layers >

**Fields and farmland** (`wce_tile::fields`, `tile_document/fields.rs`, `fields_panel.rs` under a field area's properties in the

**Biomes** (`wce_tile::biomes`, `tile_document/biomes.rs`, `biomes_panel.rs` in the Inspector: the Create panel's Vegetation > Biomes

**Tile variations** (combined projects; `wce_tile::variations`, `tile_document/edits/variations.rs`, `combine_ui.rs`, the Scene panel's `shown_variation_checkboxes`; [plans/tile_variations.md](plans/tile_variations.md), the format in [formats/tile_wce.md](formats/tile_wce.md)): a tile's variations (a settlement's `minor`, `small`, `medium`; random alternatives `aa`, `ab`) as **one tile** the user works on, what they share kept once. Layers, groups, variation folders and terrain layers say which variations they belong to (all by default); an export makes the variation it is asked for, everything that belongs to it and nothing else. Only the editor knows combined projects: the kit and the packs get each variation as its own tile.
- **Combine** (Tile > Variations > Combine..., a tile of several variations not combined; `tile_combine [--ref <v>] [--align] <v>...`): the dialog lists the entry's variations, where each comes from (its project in the projects, else the kit, else the packs, decompiled when read) and the share of its instances the reference has too; none is ticked at first, and nothing combines by itself (opening a tile never offers it). The **reference** (the one sharing the most at first) is the project's first variation and gives the terrain's base. The scenes are merged (what every variation has once, the rest in folders for its variations, an instance whose height alone differs kept once with each variation's height); the terrains become **patches that build on each other**: each variation in turn, against what the patches so far give it, a 64 x 64 block it differs in goes into a "Variation patch" layer of it and every later variation with that block the same (`small`'s changes one layer of `small, medium`, `medium`'s own one of `medium` over it); heights are compared as each stores them. Files every variation has the same are kept once, the others in `variations/<v>/` (a decompiled tile's `decompiled_terrain` and `decompiled_vegetation` among them). **Align heights** (the checkbox): a level that is another's copy saved again with another height range (its ground a little higher or lower) takes that one's heights where it is the same (per block, read the way that agrees with it) and that one's range, and its buildings' own heights that only followed the shift go; its export changes there (the report says how much). Before anything is written each variation is written back from the result and compared with its source (its scene through the conversion for TEd, its maps, its files; an aligned one with its aligned heights). Then the projects that went in are moved to `<projects>/backup/combine/<when>/`, the combined project takes their place and the tile opens again. The kit and the packs are never written. The tile must be saved first.
- **The view: everything, with filters.** A combined project shows every variation at once, each element once; **Show:** over the Scene panel's tree (and Tile > Variations > Show; `tile_variations_shown <list|all>`) has a checkbox per variation: what belongs to no variation shown is hidden, as a hidden layer. A filter of the view, not an edit and not saved; the last one shown can't be unticked. One shown alone is exactly its tile, terrain too. An element several variations have that differs between them (a building's height on each level's ground) is drawn as the first shown variation it belongs to has it; the first shown is also the tile's own (its height range, what the editor makes over the terrain). The terrain is the base with the layers of the variations shown; the minimap follows.
- **Editing**: an edit changes every variation the element is in. A move moves each by the same amount (each keeps its own height on its own terrain); another value becomes the same in each. Something meant for some variations goes in a layer, group or folder of theirs: the Scene panel's **Variations** column (an element's own bright, inherited dimmed; a click on a layer's, group's or folder's ticks them; its header's left edge resizes it), the Inspector's checkboxes for a layer, a group or a folder (`tile_variations <list|all>`; an instance shows its folder's, read-only). The tree's context menu: **Move to a variation folder** (*Only in <v>*, *In all but <v>*; `tile_to_variation_folder <list>`) and **Split for a variation** (`tile_split_variation <v>`: the selection copied into a folder for it, the originals into one for the others, the copies selected; one undo step). **Tile > Variations > Tidy** (`tile_variation_tidy`) joins side-by-side folders with the same contents and takes away folders holding every variation of their parent, empty ones and those of no variation; no export changes. New elements go into the working layer and get its variations. Problems lists tags naming a variation the project does not have or the parent excludes, and folders of no variation.
- **Terrain patches**: the Terrain layers section has a variations button on every layer (its checkboxes in a popup) and **New layer for...** (the variations ticked): a patch of `small, medium` under one of `medium` builds a level on the one below. A layer in no variation shown is dimmed, and the section warns when the working layer is in none (the paint would not show).
- **Made per variation**: the procedural roads' terrain layers and pieces and the kit walls' height layers and layout are made for the tile's variation (the first shown), laid on its ground (their layers' owners name it); an export makes those of each variation it writes. The prefab references' ground is made for every reference, its layer of the reference's variations. **Generate SiegeAI** needs one variation shown alone: its layout goes into a layer of it alone (an earlier generated one of it replaced; the layouts in layers other variations share are left as they are).
- **Exports**: File > Export ticks the variations to write (all at first; the commands' `--variations a,b`). For Assembly Kit writes each in its folder of the kit and the entry with every row; As exported tile and To mod pack compile each; **Tile > Launch in game** asks which variation (`tile_launch_game --variation <v>`), with its deployment zones. Each is first written as a project of its own under `<projects>/build/variations/raw_data` (`variations::materialize`): its scene, its maps composed from the layers that are its (its height map in its row's range while the heights fit it, else in theirs, the entry written with it), its files. The map context and the Terrain tool find a combined project's variation the same way (`sources::find_tile`), written again when the project changed (a stamp).
- **Separate** (Tile > Variations > Separate > <v>; `tile_separate <v>`): the variation made a project of its own again in its folder and taken out of the combined project (what only it has, the layers only it has); the others are checked to stay as they were before anything is written, and the old files go to `<projects>/backup/separate/<when>/`. The tile is saved first and opened again. The last variation separated leaves no combined project.

**Tables in files** (`wce_tile::user_files`, user 2026-11-16: buildings added without a rebuild; distributed with the app): `walls.toml` (the wall bases: their families' numbers and each base's pieces, `wce_walls::profile`), `bridges.toml` (the road bridges' bases, `wce_walls::bridge`), `road_fences.toml` (the dirt road types' fences and joiners, `wce_tile::road_fences`) and `road_types.toml` (the dirt road types: name, width, lanes, `wce_tile::road_dirt::styles`), one set per game (user 2026-11-16: a game's buildings are not another's; `tables/attila`, `tables/rome_2`, `tables/thrones_of_britannia`, read for the game the settings select; each game's lists only what its packs have, checked by `wce_walls` example `tables_check` against the game's own files: Rome II has no dirt road type, its packs have none of the decals), in the repo's `tables/`, packaged as the release's `tables/` folder (`.github/workflows/release.yml`) and read from the app's folder (`user_files::tables_dir`: `<folder of wce.exe>/tables`, else the source tree's for a build run from `target`; a missing vanilla file is logged and the copy built into the editor for that game used). **Mods' tables** (user 2026-11-16): every `<stem>_*.toml` beside a vanilla file (`walls_tdd.toml`) is read over it, in their names' order, while a mod pack loaded in the editor (`selected_mod_packs`) has a name starting with its top-level `mod_key` (`tdd_pack1_main_`; empty: always, the user's own changes; none: not read, logged): its entries replace those of the same key or name (a wall family's numbers one by one) or are added. **Procedural roads** (`WceRoadSpline`, Create panel with the roads; `wce_tile::roads`, `tile_document/roads.rs`; [plans/procedural_roads.md](plans/procedural_roads.md)): a line whose road is generated: the ground under it smoothed to a maximum grade, banks that widen to hold a maximum side slope, a texture and a ground type, each in a layer the road owns, made again when the road or the ground under it changes; its road type's pieces laid along it, end to end, bent to it by overrides (`wce_tile::road_layout`: straights, curves, a corner on each sharp point, `road_sharp` or the Polygon panel's checkbox, an end piece on each free end, fences along either side and round its corners and junctions when `road_fences` asks for them, of the kind `road_fence_type` picks (the type's `fence` or a named one, from `road_fences.toml` in the settings folder, which the user edits to add fences without a rebuild; a point's `road_fence` wins), joiners on the joints between them (a fence piece's `joiner` group, or `road_fence_joiners`; `road_fence_joiner_ends`), tilted to the ground, `road_fence_damage` of them destroyed; a point's own `road_width` narrowing or widening the road to it from its neighbours; a road's end within 8 m of another road is taken onto it and makes a T junction there, two roads crossing an X junction), fords over water less than 0.75 m deep (the road on the bed, the terrain's heights left alone, ford pieces), and bridges over deeper water (their deck `road_bridge_clearance` over it, the road climbing to it) and over drops, generated too: a kit bridge (`road_bridge`: wood or stone) bent along the road, widened to it, its posts down to the ground (`wce_walls::bridge`); an export makes them as walls are made, into the same packs. Generated wall and bridge pieces carry their bases' collapse animations, warped as their meshes are (`mesh::warp_collapse`); a wall's or a road's **Destruction (preview)** row (`destruction_preview`, 0 to 3, the editor's only: the exports do not read it) shows its pieces at that level, raising it plays their collapses as a building's level does (`Tile::show_generated`, collapse.rs; a wall's pieces are made with every level from the first time it is above 0, before that with their intact meshes alone, and draw nothing while the new ones load). Each bridge and ford gets an `AIH_BRIDGE_CROSSING` hint in an export, as vanilla's crossings have; `tile_export_text <file>` writes the scene as an export reads it. Roads and walls are made off the editor's thread (`tile_document/jobs.rs`), put in place when they are done; `tile_wait_jobs` waits for them (scripts), and an export waits for the roads. TEd never sees the element; an export writes the terrain it makes and its instances as the layer *WCE procedural roads*. **Road pieces** (`wce_tile::road_pieces`, being redesigned): prefabs in the projects' `art/prefabs/roads_proc/<type>/`, keyed `road_<type>_<piece>`; the placeholders of `roads_proc/base/` (guides only) are written when the prefab library is first scanned for a game, where missing or an older generation nobody edited (`wce_generated`), and so are the first road types, `roads_proc/dirt` and its one-lane `roads_proc/dirt_track` (`wce_tile::road_dirt`; the Inspector's road type row lists the library's types and puts the road at the chosen one's width), made of the kit's road decals when its `global_dirt_road_*` prefabs have them or the game's packs do (`road_dirt::game_has_decals`: Thrones of Britannia's kit has no prefabs, its packs have every decal). A piece marks its road with `WceRoadGuide` lines (`guide_role` centre, edge, verge or port), shown on the Prefab tool's stage only and dropped by every save for TEd; a part's own `road_anchor` (surface, edge, verge, fixed) overrides where it stands.

**Export as prop** (`wce_tile::export_as_prop`, a checkbox of a building in the Inspector, kept in tile.wce as `wce_export_as_prop`; newer games' tools have it, Attila's TEd does not): the building stays a building in the editor, and an export writes it as plain models, one `SIMPLE_MESH_INSTANCE` per piece at the building's place, scale and destruction level (the game ignores a building's scale, so the Inspector's **scale** row and the Scale gizmo work on a building only while it exports as a prop; off again the value is kept and greyed out, and the viewport draws scale 1, as the game does; docs/re/buildings.md), so that it has no collision, destruction, effects or logic and leaves the building lists, the terrain stamps and the capture locations (`TileDocument::text_for_export`: the game export and Save for Assembly Kit read the same converted text; tile.wce keeps the building). A building with a `capture_location` has the checkbox greyed out, with a tooltip saying why (that one, with a piece that has no plain mesh (the siege engines), or without models in the mounted files stays a building, and the log says why). BOB takes every simple mesh for a water plane and stops at the first that is not one: the models' names end in `__wce_prop` and the editor's stage B leaves them out (`compile::water_planes`), so the water map does not change; TEd's own export has no such exception, and Save for Assembly Kit warns when water planes come after such a model. In a prefab: the box on an item of a placed copy is that copy's override, Edit prefab's is the prefab's and reaches every tile that places it; both convert when the tile is exported. Save prefab for Assembly Kit converts them too (`PrefabLibrary::save_for_kit`), as a tile's save does, and says in the log that a tile placing the prefab loses the water planes after those models in TEd's own export: the prefab cannot know them.

**New tile** (`wce_tile::new_tile`, `new_tile_dialog.rs`; the review of TEd's New Tile in [plans/workflow_review.md](plans/workflow_review.md)): **File > New tile...** asks for a name (no spaces, lower-cased), the size (1..64 cells a side, default 8), the terrain height (default 10, in the height map's units as TEd's: wce shows 5 m) and the density (32, 64 or 128; above 16 cells a side it drops to 32 unless chosen), shows the files' size, and writes a **project** at once: the entry `terrain/tiles/battle/_tile_database/TILES/assembly_kit_<name>.xml` (tile set `assembly_kit`, variation `battlefield`, TEd's flags, texture groups and colour, min_height = the height, scale 50) and in `terrain/tiles/battle/assembly_kit/<name>/battlefield` `tile.wce` (empty), a flat `height_map_0.png`, `blend_map.tif` (all the first texture group) and `ground_type_map.png`, each `(cells + 2) * density` pixels a side; then it opens. A name a project, the kit's raw_data or its working_data already has is refused. `tile_database.bin` is not touched (the export compiles it from the entries). Command `new_tile <name> [x] [y] [height] [density]`. **The height range follows the terrain**: the heights are kept in metres, so the brushes are not held to the entry's range; a save that writes the height map fits min_height / scale to its lowest and highest samples as TEd does (a flat map: scale 50; kept when within half a step of the old range, so an unedited map keeps its numbers) and writes them into the entry next to the saved tile (the message says the new range). Only a folder the entry points to (its location and the variation) gets the range: saved into another one (File > Save as elsewhere, a tile without an entry) the heights keep the range they are stored with unless they left it, no entry is written, and the message says the folder opens again without its height range, size and colour. **File > Save as** of a tile into a `battle/<set>/<name>/<variation>` folder of the projects is **Tile > Save tile as...** (a new tile with its own entry; `TileDocument::save_as_new_tile`).

A landscape instance stands on the terrain: moving it in x / z (gizmo, G grab, the Inspector's world position, `tile_move`) puts it on the terrain at the new place, and a y that is dragged or typed is ignored (the y handle does nothing, as TEd refuses a typed y); a freeform one has any y. Landscape -> Freeform keeps y, Freeform -> Landscape snaps. **A height stroke carries the landscape instances under the brush with the terrain** (their y changes by the change of the height under each; the same undo entry as the stroke, so undo puts both back; hidden and locked ones follow too; freeform ones stay). `lf_offset` is not used: it is 0 in every tile TEd wrote and equals the y in the older CA tiles. The **Inspector** has TEd's `placement` combo (Landscape: Above / Freeform) for instances and says how far a landscape instance is from the terrain; the **Tile panel**'s *Debug* section has the placement (counts, Landscape / Freeform / Snap to terrain for the selection, layers included, and *Report off-terrain* with a tolerance: a list of the landscape instances that are further off, *Select them*, *Snap them*; polygons, lines and what only holds them are left out: they have the mode, but no height of their own), a combo next to *Add* for the placement of new buildings (default Landscape), and *Drop to terrain* snaps the selection whatever its mode. Duplicating a landscape instance puts the copy on the terrain. Commands: `tile_placement <what> landscape|freeform`, `tile_snap <what | all> [freeform]`, `tile_set_world <x> <y> <z>`, `tile_report_off_terrain [tolerance] [layer]`; tests `assert_placement`, `assert_on_terrain <what> 0|1 [tol]`, `assert_off_terrain_count <tol> <n>`, `assert_placement_counts <landscape> <freeform>`.

**Ground** (Phase 3): the terrain is drawn by the game's own terrain shaders (`docs/re/terrain.md`, "The tool's terrain pass"): the tile's blend / index maps (from `blend_map.tif`), a normal map from the live heights and the textures of a climate. The **ground views** (`ground_views.rs`) are a chip at the viewport's top right (the layers icon, lit while the view is not the colour or the automatic no-go areas show; left of it the placement chips while placing), mirroring the weather chips at its top left. Its popup: the *view* (colour, blend groups, ground types, protection, water depth: TEd's debug views of the tile's maps, drawn as flat images; picking one turns the blend on), the water depth view's tools (*shallow from*, *deep from*, *Paint water ground types*), and the *automatic no-go areas*, *water (rivers)*, *sea at 0 m*, *sea state*, *procedural trees* and *grass*. The Ground brush still shows the ground types view while it paints and gives the view back after. The **automatic no-go areas** are the ones the export adds by itself (BOB's `terrain_outlines.xml`: the ground steeper than 30 degrees in the final heights, less the go regions, traced, simplified and filtered as BOB does, `terrain_outlines::no_go_outlines`), worked out with the water depth from the tile as it is in memory (stage B's `water_fields`, `water_view.rs`) once it has settled after an edit, and outlined in red on the ground. The chip's popup (laid out as the other chips': View, Water depth, Water, Vegetation, Checks) also has the *Blended ground* check box and says what is shown or why the plain tiled texture is used (no blend map, no database entry, no textures), and which game shaders did not load; the chip is lit while the blend is off too. (The Tile panel's *Ground* section that held these is gone.) Changing climate or season rebuilds the texture arrays. Commands: `tile_terrain blended|flat [climate] [season]`, `tile_ground_view colour|groups|ground|protection|water`, `tile_auto_nogo [on|off]`; test `assert_ground blended|flat [textures n] [climate]`.

**Minimap** (`minimap_panel.rs`, `tile_document/minimap.rs`): a panel with the open tile from above, north (+z) up and +x right, over the height map's area (its border too; the tile's edge is the white frame), with a north arrow (the compass's north). A **base** picture under **layers** turned on and off. The base is picked from a chip at the map's top left (the north arrow is at its top right), independent of the viewport's view: the ground views (the *colour*, the game-look colour of the look's climate and season, the CPU stand-in of the blend, `bake_terrain_colour`, with the sea over the ground under 0 m while *sea at 0 m* is on and the tile has a sea (a coastal set's tile, `tile_sets::coastal_set`: the game draws no sea on another's low ground); *blend groups*, *ground types*, *protection*, *water depth*), each baked on a thread at 1024 pixels from the maps in memory (`Tile::minimap_ground_bake`; again when the look or the map it reads changed, the last picture shown meanwhile), the *height* (a colour ramp from the lowest to the highest ground, shaded from the north-west, the ground under 0 m blue on a coastal set's tile; made again at most every 0.3 s while the heights change), the *radar* (the tile drawn as CA's hand-made `loading_screen_radar.jpg` are, [plans/radar.md](plans/radar.md): redrawn at most every second after an edit; every export and launch draws it into the exported tile, each variation of a combined project its own, unless the project has a hand-made one; `radar_save [path.png]` writes it, a combined project's into the viewed variation's own folder) or *none*. The layers: the **siege AI** (what `wce_siege::svg` draws, in its colours: no-go regions, the buildings' hard outlines and the fort pieces, the perimeter, the nodes' rectangles and Boundaries, streets with their sides, area connections, wall and palisade edges, approaches, separators, a port's deployment lines, beaches and beach approaches, the captures), the **deployment zones** (every group: the defender's, alliance 1, blue; the attacker's red; additive filled, subtractive darkened, guerrilla outlined), the tile's **cells** (the entry's: the valid ones outlined in the highlight colour, the others darkened; the tooltip names the cell), the **automatic no-go areas** (filled red) and the **camera** (its eye, its horizontal field of view and the orbit's target). The siege AI is read again after an edit once the mouse buttons are up (tens of milliseconds on a big tile: Rome's 25 000 buildings). The left button moves the camera there (held: it follows; the orbit's target goes onto the ground there, the free camera keeps its height above the ground), the wheel zooms around the cursor, the middle button pans, *fit* shows everything again. The Tile panel's *valid cells* show the minimap's colour over them at the opacity of the *ground colour* slider (default 0.75; 0 hides it). Command: `minimap [colour|groups|ground|protection|water|height|radar|none | siege|deployment|cells|nogo|camera on|off | zoom <k> [x z] | goto <x> <z>]`.

**Water** (Phase 4): river ribbons from the `SplineRiverInstance` elements and a sea / lake plane for the sea, coast, lake and river-mouth tile sets, drawn by the renderer's water pass with the game's own shaders (`docs/re/water.md`: `rigidriver`, `waterplane` and `waterrefraction`: refraction of the lit scene, environment reflection, sun glint, fog); the Tile panel's *Ground* section has the *water* check box and says what was found. Rivers are drawn whatever the spline layer's eye says (TEd does too). Commands: `tile_water on|off`; tests `assert_water <n>`.

**Building technology** (`tile_document/tech.rs`, `tech_chip.rs`; TEd's Building Settings): a chip at the viewport's top right, left of the ground views' (a dashed square, lit while something is drawn), opens a popup that picks what of the buildings' logic files (`<key>_tech.cs2.parsed`, read once per key through rpfm's `Cs2Parsed`) and their pieces' `.meta` files is drawn over them. Nothing is drawn until something is ticked (all off at the start, kept for the session only: a view setting of the tile like the polygons', not in `settings.toml`; the Game view hides it like the other overlays). The kinds, by group, each with a colour swatch and a tooltip: *Collision* (the collision mesh's triangle edges, gate collision, the hard outlines that block units, soft collision cylinders), *Walking and fighting* (the footprint outlines, platforms filled and coloured by flag, pipes by type, formation lines by action with their facing, docking lines), *Siege and effects* (arrow emitters, action effect nodes, attached buildings, the `.meta` particle emitters: bright when they play while the building stands, dim on events, a box for volumetric ones) and *Frames* (the bounding boxes, the minimap flag). **Buildings**: *In range* (every building within a range of the camera, 30..1000 m, the nearest first, at most 600 000 lines; drawn again when the camera moved a sixth of the range) or *Selected* (the selected buildings, or those in a selected layer or group); *Draw through the models* (on by default: the hulls are inside the models) turns the depth test off. **Checks**: *Overlapping buildings* (TEd's `detect_building_collisions`) outlines in red, with a pole above, the buildings whose footprints (the hard outlines, else the state's box) overlap, and joins each pair by a line; footprints that only touch (within 0.2 m) do not count, two on the same spot do, and a selection is tested against what stands near it; *Most destroyed state* (TEd's `force_show_highest_destruct_level`) draws every piece's last destruction state instead of the one the building shows (the models do not change). Footprints are laid on the ground (their files have no heights; the game lays them on the terrain), a point every unit, and drawn again when the heights change. **Procedural walls** are drawn as buildings too (user, 2026-11-04: to find their pathfinding and formation line bugs): their preview pieces' logic files, made with the pieces (the meshes' intact state), each piece at its frame; a wall is as far as its nearest piece, *Selected* takes a selected wall, the overlap check leaves them out (they stand against their towers), and a wall made again draws its new pieces (`scripts/tile_wall_tech.txt`); `wall_tech_check [gaps stacked loose]` checks the selected walls' pieces together in the world (stretches no footprint covers, platforms over one another, formation line ends on no platform; with numbers, a test). The state drawn is the instance's: its saved `destruction_level`, a piece's own (the Inspector), and a hidden piece draws nothing; a piece whose `show_collision` is ticked draws its collision whatever the chip says. ASSUMPTION: a soft collision's `point_1` is (radius, height); a docking line lies 0.2 above its piece's ground plane (no shipped Attila file has one). Commands: `tile_tech [all | none | on|off <kind>... | scope all|selected | range <m> | xray|highest|detect on|off | fill <0..1>]` (no argument logs the settings; kinds `collision gates outlines soft footprints platforms pipes formation docking arrows actionfx attached emitters bounds flag`), test `assert_tech <buildings> [min lines] [collisions n]`; `scripts/tile_tech.txt` (in `tile_check.sh`) and the gate `tech_check` (every logic file of the game reads into shapes).

**Procedural trees** (*Trees* in the ground chip, `tree_list [on | off | auto | <category>]`): generated by the editor as BOB would (`wce_tile::vegetation`) from the tile as it is: its seeds, edited height map, exclusion polygons, static trees, the blend map as painted (the saved `blend_map.tif` until it is loaded) and the Assembly Kit's vegetation parameters, for the ground's climate as the game picks it (the climate's own category when the kit has one, else `default`; `tree_list <category>` picks another, `auto` goes back). The packed tile's lists (`<list>.tree_list.bin`) are not drawn while the trees can be generated: a decompiled tile's generated trees came from seeds it does not have; without the kit's parameters
(Rome 2), outside a kit's `raw_data` or without `<Vegetation>` seeds, the climate's packed list (its own, else `default`; in the tile's
folder, the game files or `decompiled_vegetation/`) is drawn as shipped instead (the chip says so). They draw with the static `VEGETATION_INSTANCE`s, not selectable; a generated list holds the static trees too, and those standing where a static instance stands (shown or hidden) are skipped, so hiding the instances' layer hides those trees. The trees and the grass are generated again by themselves when what they are made from changes (`Tile::follow_vegetation_inputs`): the
heights, the painting, the seeds, the exclusion polygons, the static trees, the climate (the grass keeps its patches and takes the climate's
models); looked at when the history, heights, painting or climate move, done once nothing has moved for 0.4 s (a drag or a stroke: at its
end). *Regenerate* makes them again by hand. Generation runs on a thread of its own (`vegetation::Job`; the grass's too): what it reads of the tile (the heights, the painting, the seeds, the static trees) is taken on the UI thread, the generator runs there, and the trees and grass drawn stay until the new ones are done (0.01–0.1 s for most tiles, seconds for the largest: custom_mont_blanc, 51k trees; middle_men_port_a/minor, 32k trees and 700k grass patches). Placement as the game's (`docs/re/vegetation.md`): terrain height unless freeform, scale byte / 127, the game's random yaw for one worker, tilted to the terrain (static trees too). The static instances draw the model their key becomes on the trees' climate (`per_climate_tree_conversions.xml`: olives turn to oaks on ROME_Atlantic...), as the game's lists have them. Trees (and grass) draw their season's diffuse (`<name>_<season>_diffuse`, the ground's season) where the game has one.

A project decompiled before 2026-11-12 has one exclusion polygon over the whole tile (BOB generated nothing there); opening it replaces that polygon with polygons around its static trees (`tile_document::convert_whole_tile_exclusion`, docs/formats/tile_decompile.md) on
the project, before the document is made from it (so it draws from the start); the tile opens modified (no undo entry): save to keep it.

**Grass** (*Grass* in the ground chip, `grass on|off|regenerate`): generated as BOB would from the tile as it is: its `<Grass generation_seed>`, the blend map as painted (the saved `blend_map.tif` until it is loaded) and the kit's `max_grass.xml` (exact to BOB on 119 of 125 kit tiles); Made again by itself when the heights, the painting or the seed change (see *Procedural trees*); *Regenerate* by hand. The packed tile's `default.grass_list.bin` is drawn only when the grass can't be generated (no `max_grass.xml`: Rome 2; outside a kit's `raw_data`; no seed), as shipped (the chip says so): a decompiled tile's came from a seed it does not have, and it goes stale with the first edit of the heights or the painting. Drawn by the renderer's grass pass with the game's rigidgrass shaders, within 100 m of the camera (where the game's vertex shader has sunk it into the ground); models from the climate's `terrain/vegetation/battle/grass/<climate>/` folder, else `default`. Placement as the game's: on the terrain, tilted to its normal measured over the patch's size, patches on slopes over 0.7 rad left out, the game's random yaw for one worker; the season's diffuse (`<name>_<season>_diffuse`) where the climate has one; grass casts shadows.

**Tile links** (Phase 6a, read-only; `docs/re/tile_links.md`): the Tile panel's *Tile links* section is a map of the entry's link targets and rules (`links_editor.rs`: the tile's cells, the ring of neighbours' cells round them, a colour per link set; a click picks a link and moves the view along to its cell, at the height, angle and distance it had, or adds a target on the tile and a rule around it; a right click removes one) and *show on the ground* draws the cells they name coloured by link set. The tiles that can follow are looked for in the tile's own database over the projects', the kits' and the packs', mods included. Commands: `tile_links [on|off]` (no argument: log them); tests `assert_links <targets> <rules> [drawn 0|1]`, `assert_link_cell <x> <y> <x0 m> <z0 m>`.

Entry commands: `tiles [words]` (the browser's rows), `tile_entry` (log the entry), `assert_entry <field> <value>`, `assert_tiles <n> [words]`; test helpers `gizmo_drag <x|y|z> <pixels>` and `cam_info`. Extra commands: `tile_mode`, `brush`, `grab_to x z`, `tile_click`, `tile_click_ground`, `tile_drag_point`, `draw_polygon`, `tile_diagnostics` and the tests `assert_instances`, `assert_type_count`, `assert_world`, `assert_world_xz`, `assert_height`, `mark_height` / `assert_height_delta`, `assert_selected_type`,
`assert_at_cursor`, `assert_mode`, `assert_grabbing`, `assert_file_exists`. `mouse move|click|drag|wheel|off x y` (pixels or `50%` of the viewport image) drives the same ImGui events as the real mouse; in fixed-step runs the real mouse is ignored. `where [x y | on | off]` prints the camera's, its orbit target's and the cursor's coordinates (scene and game units; in a map context
also the map cell, and the cursor's height above the sea), `x y` probing the ground under that pixel; the same readout sits in the viewport's
bottom-left corner (View > Coordinates). With a tile open the game units are the launched battle's (`coords::BattleFrame`): centred on the
tile, height zero at the map's sea level at a map placement and at the variation's `min_height` (its number, as scene units) for the tile
alone, as the cameras of in-game captures fit (western_city_rome/small: the editor's (386.3, 9.8, 333.8) is the game's (-251.5, 44.5,
-356.5)). `luma` logs the auto exposure's black and white points, `cb <buffer> [variable]` a game constant buffer's values. View > Fog turns the distance fog off (the fog pass and the rivers' own fog), as `gfx fog off`.

`tile_studio.exe` (and its own renderer) was removed in Phase 8; the tile captures of `scripts/shots.sh` are the render regression.

Most edits of a tile publish only what they changed. Attributes (a name, a spline's values) refresh their items, a property the file lacks or a building's key makes its item again, a moved layer or group refreshes what is below it, the eye and the cursor add, remove or lock the difference (`tile_document/shift.rs`). Move to layer, group, ungroup, prefab updates, Resize, Restore walls and Generate SiegeAI publish the tile again. The minimap reads the siege overlays again only when something that feeds them changed (`Tile::siege_version`), and keeps each building's part.

**References (`ref_human`, `ref_unit`):** the Create panel's References category places real soldiers in the tile to measure the scale against, as many as
wanted: `ref_human` is one soldier, `ref_unit` a whole unit, its men from `main_units.num_men` at the game's unit size (`gfx_unit_size` in its preferences, read
again every few seconds), in the ranks and close spacing of its tables. They are tile elements like any other (moved, turned, grouped, undone; a click on any of a
unit's soldiers selects it), saved in `tile.wce` as `WceRefHuman` / `WceRefUnit` and dropped from anything TEd or the game reads. The Inspector picks the unit,
faction, animation slot, soldier and colours; an edit goes to every selected reference. They stand on the ground under each man, or level at their own height when
freeform. They aren't drawn in the Game view. Script: `tile_ref human|unit <x> <z> [unit] [faction] [soldier] [slot]`, `tile_ref status`.

**Tape measure (`WceMeasureLine`; TEd's Tape Measure, `TAPE_MEASURE_LINE`):** the Create panel's References category draws an open line of points on the ground
(clicks; Enter finishes, Esc cancels), as many as wanted. TEd's measure lines never reach a file it writes, and some versions lose them on save; ours are tile
elements like the polygons (points edited, moved, hidden, undone), saved in `tile.wce` and dropped from anything TEd or the game reads (Save for Assembly Kit lists
it as dropped; the game export is byte for byte the same with or without one). `wce_tile::measure` works out, for each stretch and the whole line, the length
along the ground (the terrain sampled every 0.5 m between the points), straight (3D), on the map (x and z) and the rise and grade (rise over the length on the map;
the whole line's from its first point to its last). The points stand on the ground, as a landscape polygon's do. The viewport labels every line shown with its length
along the ground (and straight, when it differs) at its last point, the selected one each stretch at its middle, and the line being drawn at the mouse; the
Inspector below the grid shows the totals and a table of the stretches. Commands: `tile_measure` logs the selected line's lengths, `assert_measure <ground>
<straight> <map> [tol]` tests them.

**Angle finder (`WceAngleFinder`; TEd's `ANGLE_FINDER_INSTANCE`):** next to the tape measure in References: three clicks on the ground (an arm's end, the corner,
the other arm's end; the third finishes it), kept and dropped as the tape measure is. It has three points always: inserting or removing one, or making one with
another number, is refused. `wce_tile::measure::angle` gives the angle at the corner seen from above (on the map) and in space (with the arms' rises), and each
arm from the corner out as the tape measure's stretches (along the ground, on the map, grade). The viewport draws an arc at each one's corner (a third of the
shorter arm, 1 .. 25 m) with the angle beside it, the one being drawn included; the Inspector shows both angles and the arms. Commands: `tile_angle`,
`assert_angle <on the map> <in space> [tol]`. TEd's other instance types and what the editor does with them: [formats/tile_ted.md](formats/tile_ted.md).

## Unit tool (`wce_unit_tool`)

Edits a unit's looks: its **variant mesh definitions** (VMDs), worn by a unit of the DB in the viewport ([plans/unit_editor.md](plans/unit_editor.md);
the rendering is [plans/units.md](plans/units.md)'s). The document is one `.variantmeshdefinition` (`VmdDocument`, the lossless `XmlDoc`
as in the Weather tool: value edits change their span, structural edits are snapshots, one undo entry per drag or typing), opened from
**Unit files** (every definition under `variantmeshes/`), from **Units** (a `unit_variants` row: its definition, worn by its unit and
faction) or File > Open. Save writes `loose/<its path in the packs>`. A file that isn't XML (TDD has 11) opens as the game most likely
reads it, with a warning, and Save writes that repaired text.

- **Preview as** (Preview panel): the unit and faction wearing the file give the skeleton, animations, mount, size and colours; remembered
  per file (`[games.<id>.tools.unit] preview`), else a unit that wears it (searched on a thread for a part's file), else the game's default.
  The unit's own definition (or its mount's) is replaced by the document; a part's file (a helmet's, a shield's) is worn where the unit's
  definitions reference it, at any depth (`Pins::focus`), and alone when they never do. The panel says which.
- **Soldiers**: the seed (the editor's generator, not the game's), up to 16 side by side, the animation slot looped, play / pause and the
  time, own colours. **The stage's weather** (`weather.rs`) is set as a tile's: chips at the top left of the viewport, beside the compass
  (climate, season, precipitation, time of day, climate change; the cloud lists the files they let through, with the campaign and snow
  attrition filters, and a click lights the stage with one; the pencil opens it in the Weather tool), on the packs' variation database
  (campaign `default_map` until one is picked, always a land battle); a filter the file no longer passes gives way to the first dry one
  without snow that does. Climate and season pick the ground's grass too (`terrain/textures/battle/<climate>/grass/0_<season>_diffuse.dds`,
  else the climate's summer, else the default climate's). **Pins** force what a slot shows (the seed's, nothing, or an alternative), a mesh's tint and its
  `.texture_array` decal; by default the slots above the selected node show it (*Show the selection*), and *Isolate* draws only its parts.
  A pin changes only its node: each node draws from a generator of its own.
- **Structure** (`structure.rs`, laid out as the Tile tool's Scene panel): one row per node, an arrow, its icon (the root, a slot, a mesh,
  a group of slots, a reference), its name (a model's or a file's without the folder) and its details dimmed (attach point, probability,
  tints, decal); at the right edge a warning for its problems (dimmed on a closed node with problems below) and what the preview shows (a
  slot's eye: the seed's pick or nothing; an alternative's target: shown whatever the seed picks). A filter (slots, models, files), a toolbar
  (+ Slot, + Mesh, + Reference, Duplicate, Move up, Move down, Delete), a context menu per row (with Expand / Collapse all below), rename
  in place for a slot (F2, double-click; a new slot starts in it), the arrow keys, Delete, Ctrl+D, and drag and drop: a node among its
  siblings (one undo entry), a definition from Unit files onto a slot (a reference to it). A double-click on a reference opens it. The
  counts and the problems are at the bottom. The **Inspector** edits the selected node: a mesh's model, decals
  and imposter (with a filtered list of the packs' files), its colour mask, tints; a slot's name, attach point (the weapon bones and the
  points of the model above), probability; a reference's file; attributes the panel doesn't know as text.
- **The viewport**: a click selects the part under the cursor (a ray against the soldiers' parts as posed that frame, on the CPU:
  `wce_render::skinned_geometry`); the selected node's parts are outlined as a selected building is (a `selection_mask` overlay of their
  triangles, made again each frame). A part from another file selects its reference.
- **Pictures** (`thumbs.rs`, on the editor's thumbnail renderer, `wce_editor::thumbnails`, which the Create panel uses too): a slot's
  alternatives in the Inspector are pictures (a click shows one, a second lets the seed pick), as are a texture array's decals; each file
  field shows a picture of what it names and a browse button (a grid of pictures or a list, filtered); Unit files and Units show pictures
  with their grid toggle. Parts are rendered alone in the previewed unit's standing pose and colours, from the front; textures are a small
  mip decoded on the CPU. Kept in the cache folder, named by what they show. A field's browser lists only what its node's slot takes
  (`slot_kinds.rs`: per slot name, the folders that hold at least 3 % of what the game's definitions put in slots of that name, and the
  slot's own alternatives' folders; models and definitions apart from decals): a `helmets` slot's model lists helmets. *Only what
  '<slot>' takes* lifts it; a slot name the game never uses, without alternatives, lists everything. `unit_takes <slot path>` tells the
  folders; the example `slot_kinds` reports them for every slot name.
- **A ship's definition** (`ship.rs`: one a `unit_variants_ships` row names, or whose root has `_dm1` slots) is drawn as the ship, not worn
  by a soldier: assembled as the game assembles a ship (its pieces intact, a part on every point of a list), with the oars and weapons of
  its naval unit's logic (the row's; with none naming the file, the unit whose ship's definition is named most like it; chosen in the
  Preview panel), as rigid meshes, its decal and weighted parts (the shields along the sides) and sails at rest by the skinned path, its
  ropes as the file has them, lifted onto its keel and framed. A click picks the nearest part from the parts' triangles at rest (the
  renderer picks only rigid meshes); the selection outlines the rigid parts by their entities and the sails and skinned parts by a mask of
  their triangles. In ship mode the pictures show parts at rest, as the ship draws them (a sail on a soldier's palette came out empty). A ship's
  part file (`variantmeshes/_variantmodels/ships/<ship>/att_sas_01.variantmeshdefinition`: its sails) is shown on the first ship row's
  definition that references it, pinned where it does, with its edits; one no ship references, but in the ships' folder, is drawn alone as a
  ship's pieces, never on a soldier.
- **Slot names** are free labels but for the ones the engine looks up ([re/variant_mesh_slots.md](re/variant_mesh_slots.md)): a soldier's
  `shield` and `weapon_1` to `weapon_4`, a ship piece's `<piece>_dm<state>`, `misc_99_dm1`, `night_lights_dm1`. The slot's name field lists
  the names the game uses (most used first) and says what the engine makes of one; a name that is nearly one of the soldiers'
  (`weapon_01`, `weapon_5`, `Shield`, `shield 1`) is a warning there and in Problems.
- **Problems**: files the packs don't have (models, decals and the textures of their arrays, references), masks and probabilities out of
  range, attach points nothing has, references that come back to the file. A click selects the node.
- **The unit's looks (DB)** (Preview panel): the previewed unit's `unit_variants` row for its faction (the definition it wears, *Wear the
  open file*, *Its own copy...* of its definition under a new name, its height scale and variation), its own colours
  (`unit_variants_colours`), and Revert. Saved at once (not undoable) as the project's own table files,
  `loose/db/<table>_tables/!wce_unit_tool`; they sort before the game's, so they are read first.

## Cross-tool composition (Phase 7)

Every open file is a `Document` in the one `DocumentManager`, whichever tool opened it. **Each tool has one document** (a tool's stand-in scene aside, the Weather tool's sample map): a tile and an `.environment` are open at once, each with its own history, modified marker and layer, but opening another tile closes the open one, another weather file the open weather file, and so on. With unsaved changes the replace prompt asks first: **Save and open**, **Discard changes and open**, **Cancel**; the old document goes only once the new one is open (if the open fails it stays, with its changes when they were discarded). Scripts: `open <path> [disk] [save|discard]` (it fails with unsaved changes and no answer, as `close` does; the tools' own open commands too: `close <doc> save|discard` first), `open_prompt <path>` opens the prompt as the menus would, `answer` answers it (`Editor::clear_to_replace`, `Editor::replace_document`). Opening a file of another tool switches to that tool (`open_path(..., switch_tool = false)` does not); a file that is open already is shown in its tool, not opened again. **The active document is the active tool's** (else its stand-in): the menus, History, `save`, `close` and the default Inspector target follow it, and switching tools switches document. Its title is at the right of the menu bar, `[Tool] title *` (amber while it has unsaved changes), and in the window's title.

## Saving and exporting

The user's work has one home, the game's **projects folder** (`Settings::projects_dir`; [plans/save_system.md](plans/save_system.md)).
**Save** always writes into it: tiles, maps and prefabs into `assembly_kit/` (the kit's layout), files opened from the game's packs (a
weather file, the weather database, a UI layout) into `loose/<their path in the packs>`. `loose/` is mounted before every pack, so a save is
what every tool reads from then on, the weather preview and Launch in game included: after each save the mounted files index the path
again (`Vfs::refresh_loose`, `Editor::loose_changed`, from `DocumentManager::take_saved`), no remount needed. **File > Revert to game's
version...** (`revert_to_game [doc]`) asks, deletes the project's copy (and the folders it leaves empty)
and opens the packs' file in its place. A file opened from disk saves in place. Each tool has its folder in the project (`Tool::project_folder`: the Tile tool
`assembly_kit/raw_data/terrain/tiles/battle`, the Prefab tool `.../art/prefabs`, the Terrain tool `.../terrain/battles`, the Weather tool
`loose/weather`, the UI tool `loose/ui`, the Unit tool `loose/variantmeshes/variantmeshdefinitions`), made with `loose/` whenever the game's files are mounted (`Editor::make_project_folders`); File >
Open file starts in the active tool's, Save as in the document's own file's folder, a file of the packs' place in `loose/`, else its
tool's folder (`Editor::save_as_start`). Save as is off for a tile and a prefab stage (`Document::save_as_blocked`: a tile is its folder and its tile database entry, a copy elsewhere opens without its height range, size and colour; Tile > Save tile as and File > Export instead). A save marks a document saved only when it wrote the document's own file: a game file's copy outside its place in `loose/`, or a map's outside its projects folder, leaves it unsaved, as its own file lacks the edits.

Everything written for the game or for TEd is under **File > Export**, from the active tool (`Tool::export_menu`); each entry asks for its
destination and remembers the last one per game (`Editor::export_dir`, `pick_export_folder`, `pick_export_file`; `[games.<id>]
export_dirs`), and its script command takes the destination as an argument:

| Tool | Export entries |
|---|---|
| Tile | For Assembly Kit (`save_for_kit [raw_data]`, the kit prompt when several fit), As exported tile... (`save_exported [folder]`), To mod pack... (`save_to_pack <pack>`); a combined project's variations ticked in the menu, or `--variations a,b` |
| Prefab | For Assembly Kit (`prefab_save_kit`) |
| Terrain | Built files... (`terrain_export [folder] [--wait]`; also the Export section's button) |
| UI | Layout into a mod pack..., Project as a mod pack... (`ui_export <pack>`), XML... |
| Unit | To mod pack... (`unit_export <pack>`): the project's definitions and the tool's DB files |

**Sharing projects** (File menu, after Export, from the active tool: `Tool::share_menu`; the Tile tool's in `share_prompt.rs`, the format in
`wce_tile::share`). *Share project...* (`share_project <zip>`) writes the open tile's project into one zip: every variation of its location
folder (no `.bak` or dot files), its database entry, and the projects' prefabs its references use, followed into those they use, with the road
pieces (`roads_proc/<type>`) of its roads' types; the tile has to be saved. Prefabs of the Assembly Kit are not copied: the manifest
(`wce_share.txt`) names them, and those found nowhere. *Import shared project...* (`import_shared <zip> [overwrite]`) puts it into
`<projects>/assembly_kit/raw_data` and opens its tile: new files are written, identical ones skipped; when a file differs, or the tile's
folder holds files the zip lacks, a prompt lists them and Overwrite moves each aside to `.bak` first (Cancel writes nothing). Another game's
zip, and paths that would land outside the projects folder, are refused; the tile open in the editor is not replaced under it. The import
names the kit prefabs it uses that this editor does not find.

Throw-away build files (the launch staging folders, dry runs, the export a terrain launch makes, a combined project's variations written
for its exports and the loaders in `build/variations`) go to `<projects>/build` (`Editor::build_dir`), which nothing reads back between
runs. Combine and Separate keep what they replace in `<projects>/backup/combine/` and `backup/separate/`, by date and time. Until the release, an interactive start offers once per game to move the old
output folder's edits of game files into `loose/` (`project_prompts.rs`: not the build files, `ui_xml/` exports or exports in the game's
layout; a file the project already has stays).

### Autosave

[plans/autosave.md](plans/autosave.md). Every few minutes (Settings > General: **Autosave**, on by default, every 5 minutes, 3 copies kept
per document; `[autosave] enabled, interval_minutes, keep`) an interactive session copies each document with unsaved changes into
`<projects>/autosave/`, never over its files (`wce_editor/src/autosave.rs`; the folder's layout, the rotation and the session lock in
`wce_editor_core::autosave`). A copy is made only when the document changed since its last one (`Document::autosave_stamp`), and never
while a gesture, a mouse button, a prompt or a write is under way. What a copy holds is the document's (`Document::autosave_meta`,
`Document::autosave`), written by the same code as its Save:

| Document | Copy | Taken back (`Tool::restore`) |
|---|---|---|
| Weather file | the file as Save writes it | the file opened again, the copy's text over it as one undoable edit (`XmlDoc::parse_over`) |
| UI layout | the layout as Save writes it | the layout opened again, the copy over it as one undoable edit |
| Tile | its folder in the kit's layout (`raw_data/terrain/tiles/...`) with its entry and `_settings.xml`, as a Save into another folder writes it | opened from the copy; its first Save writes every file into the tile's own folder (or the project a kit tile's first save makes), so a file that did not change gets a `.bak` too |
| Battle map | the files its edits made again, and `refs.txt` naming the others (a map's LF is large, most files are not edited) | the copy made whole (`MapDocument::complete_autosave`) and read on a worker as the map; its first Save writes every file into the map's projects folder |
| Weather database | `warscape_asset_variation_db.xml` (`Tool::autosave_work`: not a document) | the picker's working copy, edited |

A prefab stage is not autosaved. A document saved, or closed with Discard, loses its copies at once; a clean quit deletes the session's
folder (`Editor::finish_autosave`, from the app's main loop: a lost graphics device keeps them). Each editor process has its own session
folder, held by a lock on `session.lock` while it runs: a session whose lock can be taken ended without cleaning up. The next interactive
start (and the first frame after a game switch) looks for such sessions and opens **Recover autosaved work**: per document, its copies
(the newest by default), a warning when its file was written after the copy, **Restore** (opened modified, Save writes it into the
project; Undo goes back to the file for a weather file or a layout; File > Revert is refused for a restored tile or map: close it without
saving) and **Discard**; **Later** keeps them for **File > Recover autosaves...**. Commands: `autosave_now`, `autosave_status`,
`autosave_found`, `autosave_restore <n> [copy]`, `autosave_discard <n>`, and for tests `autosave_abandon` (leave the copies as a crash would).

## Layouts

ImGui runs with docking and no ini file. Each tool has its own layout file `<config folder>/layouts/<tool id>.ini` (see the folders below). Switching tools saves the leaving tool's layout and loads the entering one's; without a file the tool's `default_layout`
(DockBuilder calls; the base class builds the standard one: inspector right, assets/log/history below, viewport in the centre) is built. `layout save`,
`layout reset`, File menu entries and saving on exit (not in batch runs) manage the files. A layout that was never loaded (a switch before the first
frame) is not saved over the tool's file.

When what the Inspector shows changes to something (the selection, or the active tool's part of it: `Tool::inspector_subject`, the Tile
tool's mode, brush settings, flip panel, what it places; the Weather tool's environment file) and the Inspector is a tab behind another in
its dock, its tab is selected (`Editor::raise_inspector`, `gui::select_dock_tab`): without taking the keyboard's focus, unless the focus is
in another tab of that same dock (a dock keeps its focused window's tab in front), where the Inspector is focused. Only on a change: a tab
picked over it stays in front while nothing it shows changes; a tool switch only takes the new tool's as the start.

A plain interactive start opens the tool the last interactive session was in (`last_tool` in the settings, kept on every switch,
`Editor::restore_last_tool`). `--tool <id>` starts in that tool instead and leaves `last_tool` alone, and so does any scripted run (`--script`,
`--cmd`, `--open`, `--tile`, `--shot`, `--capture`), so that scripts start where they expect.

### Appearance

`theme.rs`: the UI font is Inter with Lucide's icons merged in (`icons.rs` names them; the private use area is taken out of Inter, which has glyphs

its own colours. Appearance > "Dear ImGui's style editor" edits the live style, to work on a theme.

### Shortcuts

`shortcuts.rs`: every key the editor and its tools react to is an action (id, scope, group, label, up to two default keys): the editor's
(`shortcuts::EDITOR`: save, undo / redo, the tools 1..9, the gizmo, focus, global / local, the camera's held keys) and each tool's
(`Tool::shortcuts`: the Tile tool's grab, box select, delete, duplicate, turn, group, copy / paste, quick add, rename, placing and grabbing keys;
the UI tool's delete, duplicate and nudges). Code reads `shortcuts::pressed(id)` / `down(id)` and menus show `shortcuts::label(id)`. A chord matches
when its key is pressed and Ctrl, Shift and Alt are exactly its own; a held action ignores Shift unless its chord has it, and a modifier key bound
alone (the camera's *faster*, Left / Right Shift) matches whatever else is held. A key may be a mouse button too, the middle, Back or Forward one (`MouseMiddle`, `MouseX1`, `MouseX2`; not the left and right buttons, which pick and turn the camera): it counts when clicked, released within 4 pixels of where it went down (a middle drag still pans), and a viewport's action reads it over the viewport only (`shortcuts::pressed_here`). Variants are actions of their own (*Turn back*, *Paste in place*).
Dialog keys (Esc cancels, Enter confirms) and text editing are not actions. **Settings > Shortcuts** lists them by group with a filter: a click on
a key reads the next key pressed with its modifiers (no action fires meanwhile; a click again stops), the cross clears it, the arrow puts the defaults
back, *Reset all*. Two actions whose keys are read at the same time (the same scope; the editor's with any; the viewport's with a tool's) may not
share a key: such keys are red, the tooltip names the other action, and OK / Apply wait until it is changed. `[shortcuts]` in settings.toml keeps
only the changed actions (`undo = ["Ctrl+K", ""]`). Commands `shortcut <id> [key 1 | -] [key 2 | -]`, test `assert_shortcut_clashes <n>`.

When the game folder is not set or does not exist the editor starts without the game and shows the first-run dialog: it picks the game, fills in the Steam
library's folder of it (registry `SteamPath` + `libraryfolders.vdf`), lets you browse, and **Save and continue** (command `setup`) writes the settings, mounts
and starts the active tool; **Quit** leaves the editor. Its mod pack list (also the toolbar's game list > Mod packs... and the Settings window's Game page) has a search
field, and drops the chosen packs that are no longer in the game's data folder (named above the list; saving the settings removes them).

`frame_cap` (Settings > Performance, command `frame_cap`, environment `WCE_FRAME_CAP`; default 60, 0 = none) holds an interactive session to that many frames per
second: rendering the scene as fast as a fast laptop display refreshes kept the GPU at 100 % until it throttled itself (to 180 MHz of 3090 on the RTX 5070 Ti
laptop, 10x slower frames). Shots, captures and frames while a script runs are not capped (perf measurements stay the real cost of a frame).

## Command line

```
wce.exe [--tool <id>] [--open <path> | --open-disk <file>] [--cam yaw pitch dist [target_y]] [--cmd "<command>"]... [--script <file>]
        [--frames N] [--shot <file.png>] [--capture WxH <file.png>] [--fixed-step <seconds>] [--live] [--background | --foreground]
```

`--shot`, `--capture` and `--script` runs are unattended: their window is created non-activating, kept out of the taskbar and Alt-Tab and put behind the other windows, so a test run never takes the focus from a game or an editor in use. `--foreground` (or `WCE_FOREGROUND=1`) brings back
the normal window, `--background` (`WCE_FOREGROUND=0`) makes an interactive run quiet too.

Everything becomes a script: `--tool` and `--open` first, then `--cmd` / `--script` in order, then `frames N` + `shot` (the whole window after N rendered frames) or
`capture` (the scene offscreen, no window involved), then `quit`. Shots, captures and scripts run on the fixed-step clock (1/60 s per rendered frame), so the same
script gives the same pixels. Exit code 1 when a script line fails.

Script format: one command per line, `#` comments, double quotes group, a leading `-` lets a line fail, `frames N` waits N rendered frames. `help` in the Commands panel (or as a command)
lists them all. Test commands (`assert_*`) fail the script when they do not hold; `key Ctrl+2`, `click_item 13`, `move 3 5 0 2` drive the same code paths as the keyboard,
mouse and gizmo.

## Gizmo and ImGuizmo

ImGuizmo wants row-vector matrices (v * M, row-major); the engine's are column-vector (M * v), so the viewport passes transposes (`to_gizmo` / `from_gizmo` in `viewport.cpp`). The gizmo moves the
first selected item's pivot (`Document::item_transform`); the change since the last frame, `new * inverse(old)`, goes to `Document::transform_items` for every selected item with a gesture id,
so a whole drag is one undo entry. Scale is accepted by the gizmo but a document may ignore it (the sample map does).

## Selection outline

The selection is drawn as an outline around its silhouette (`Renderer::pass_selection_outline`, an editor pass like picking, not a game
shader): the selected meshes and terrain (through the draw sets, as the id pass draws them) and the selected overlays go into a mask at the
viewport's size, once whole and once against the scene's depth; a full-screen pass colours the pixels within `selection_outline_px` of the mask,
solid next to the visible parts and faint (35 %) next to the hidden ones. Colour and width come from the editor (`Editor::selection_outline_style`:
the theme's highlight, 2 px times the display's scale; 2 px in scripted runs). An item without a mesh of its own is outlined from an overlay
that is drawn only into the mask (`Overlay::selection_mask`): the Tile document puts the selected markers' shapes there (`set_highlight`),
and keeps only a selected polygon's point handles in its visible highlight. A selected light keeps its reach box. With 672 wall pieces of the
Ravenna tile selected a frame takes about 0.3 ms more (it took 7.6 ms more when the selection's entities were looked up item by item).

## GPU

`libs/render/gpu_adapter` chooses the D3D11 adapter: `WCE_GPU=<part of the adapter name>`, otherwise the high-performance GPU, and the renderer logs `GPU: <name>` when it starts. Two GPUs do not round float math the same way,
so reference pixels only compare on one adapter (the gate scripts default `WCE_GPU` to `AMD Radeon`, see `docs/baseline.md`).

`WCE_D3D_NO_DRIVER_THREADS=1` creates the device without the driver's internal threads (slower): the access violations in `amdxx64.dll` happen on the driver's worker thread, after the call that caused them, and with this one happens in that call, with the editor's stack in the dump. `WCE_D3D_DEBUG=1` is the debug layer, whose messages only reach a debugger.

A colour target and a depth view must have the same sample count: with MSAA the particles' distortion buffer (one sample) takes the read-only one-sample depth, not the scene's. Paired with the scene's, the runtime let it through and `amdxx64.dll` crashed on its worker thread some time later; only the debug layer turns such a pair down. Its messages go to the debugger, not to the log: run `WCE_D3D_DEBUG=1` under `cdb` and search the output for `D3D11 ERROR`.
